# CLO3D API Reverse-Engineering Findings

*Status: steps 1-6 done (static analysis only)*
*Date: 2026-10-29*
*Target: CLO Standalone OnlineAuth 2026.1.336 (build 58954) vs SDK 2026.1.224 and 2026.1.336*

Detail files: `findings/01..05*.md`. Raw tool output: `raw/`. Scripts: `scripts/`.

## Key findings
1. **The SDK DLL is only an ABI definition.** All 921 exported `CLOAPI::*` methods are base-class stubs returning 0/empty; the working implementations live in the CLO exe and are reached through vtable pointers the exe gives the plugin (`findings/05`). Nothing useful can be learned about behaviour from `CLOAPIInterface.dll` itself.
2. **SDK 336 exports == installed app DLL exports** (921 each, zero diff). Both are consistent for build 336.
3. **224 -> 336 API changes** (`findings/03b_export_diff.md`): +76 exports, -1. Added: whole `GuiAPIInterface` (dock panels/tool windows/widgets/AskForm etc.), `AddSeamlinePairGroupPartial` (3 overloads, returns `SeamlinePairGroupResult`, 0 = success, failures negative), `Get/SetHiResTolerance`, pattern-to-avatar-measure APIs, button/trim helpers, `ExportThumbnail2D`, `ExportStdViewImage`, `GetActiveWorkspaceFileName(W)`. Removed: `PatternAPIInterface::RemovePatternFromAvatarMeasure`.
4. **Plugin-used functions are signature-compatible at source level.** The only header edit touching a function we call is in `ExportAPIInterface::ExportGLTF` comments (doc only; signature `(path, options, bool _bGLBinary)` unchanged), and a note that a Pattern API now runs the solver afterward. No compile break expected from these.
5. **ABI changes that matter:** `Marvelous::ImportExportOption` gained 4 vectors (`patternList`, `buttonList`, `graphicList`, `zipperList`) so its size/layout changed; `ExportDxfOption::m_bDuplicateNotch` now defaults to true. Vtables grew in Pattern (217->233 slots), Utility (401->408), Export (119->124), and `GuiAPIInterface` appeared, so slots after the insertion points moved. A plugin built on 224 will mis-dispatch on 336 and the reverse. The plugin must be built against SDK 336 and run only on CLO 336.
6. **New feature useful to us:** `ImportExportOption` component selection lists let `ExportGLTF/GLB` export only chosen patterns/buttons/graphics/zippers (one file per garment). Empty lists = whole scene (old behaviour).
7. **Vtable slot table for every function we call** (installed DLL): `findings/04_target_vtable_slots.md`. Four functions could not be resolved by name (identical-code-folded stubs): `GetAvatarProperties`, `SetAvatarProperties`, `SetBaseTextureMapImageGivenFilePath`, `SetFabricPBRMaterialBaseColor`.
8. Plugin loader contract (exe strings): exports `GetActionName`, `GetObjectNameTreeToAddAction`, `GetPositionIndexToAddAction`, `DoFunction`, `DoFunctionAfterLoadingCLOFile`. Our `RestPlugin_windows.cpp` already provides all of these.

## Not done / limits
- No disassembly of the CLO exe's real implementations (220 MB, stripped; would need a disassembler/Ghidra, not installed). Behaviour (units, return conventions, error cases) for the target functions is therefore known only from header docs and live testing, not from the implementation.
- No runtime tests against a running CLO were performed, to avoid touching the user's CLO session and licence/auth components.
- The SDK-224 vs SDK-336 slot-by-slot comparison for target functions was dropped: ICF folding makes name-by-address lookup in the SDK DLLs ambiguous. Use `diff` on declaration order in `raw/hdrdiff_*.diff` instead.

## Suggested next steps
- Install Ghidra/IDA in a user-chosen location and load the exe with the offsets above (vtable slots -> real functions) to read implementations of `ImportAvatar`, `ApplyMeasurement`-style flows, `ExportGLB`.
- Add a runtime probe in the plugin (outside this folder) that logs return values for each function above per CLO version.

### Lane F - property-stream grammar (`findings/13_avs_dan_grammar.md`, `scripts/avs_grammar.py`, `raw/avs_tree.json`)
- **Grammar fully decoded and byte-exact:** the parser re-encodes 184/184 `.avs`, 147/147 unique `.dan` and 19/19 `.osw` files to identical bytes. A block is `u8 n | u8 namelen[n] | u8 type[n] | u32 size[n] | (name value)*n`; one top-level block, no magic, no checksum. Type codes: 01 bool, 04 int32, 05 uint32, 06 float32, 0a/0b/0c/0e vec2/vec3/vec4/mat4, 0f string/blob, 14 list (`u32 count, u8 elemtype, u32 elemsize[count], elements`), 15 packed array, 16 nested block. Name prefixes (`b i ui f v2 m4 qs ba list arr map`) agree with the types.
- Tool: `python -I scripts/avs_grammar.py roundtrip|tree|dandiff ...`.
- **Corrections to lane C:** `listFeatureValues` is 62 floats in the default `.avs` and 67 in `.dan` (57 was a prefix); units cm; 47/62 match the default avatar CSV by value; pipeline fields 0, 2, 6, 8, 26, 36 correctly named; indices 1, 32, 33, 48, 52-54, 60-66 unnamed. Header field 0x30 is not 413 (that is the high dword of the 64-bit timestamp at 0x28); 0x30 and 0x3C are both 2010 (2008 for version-11 presets). The ~172 KB gap holds three more PNG thumbnails plus a 64-hex digest at zip_off-68.
- **.dan layout:** `listSkinController` (9 controllers, mm float3 positions, 144,908 physical verts, per-vertex `listJointWeight`); render meshes under `mapTransformer3D` (9 shapes, 200,134 render verts, 179,080 triangles = GLB triangle count). GLB's 606,659 vertices != 200,134 (exporter rule not derived).
- **Does the mesh depend on `listFeatureValues`?** avt_patch route: **no** (0 position bytes differ after CLO re-save). avs route: **yes** (about 73% of position bytes change; 178.5 cm body ~1796 mm tall, 137 cm ~1383 mm). Topology/UV/weights never change. Identical-input avs runs differ by <=0.0019 mm (solver noise), explaining differing GLB hashes.
- CLO does not validate the `.avt` ZIP-length field (stale in 113/379 files, all imported fine) - based on pipeline success, not a dedicated test.
- Unknown: what the 64-hex digest covers, `listMeasureMode` values 0-5, skin controller -> render shape mapping, why CLO ignores `listFeatureValues` when loading `.avt` (`bHeightLinked`/`enLastUpdateMode` untested).

### Lane H - measurement import internals (`findings/15_measurement_import_internals.md`, `scripts/xref_rip.py`, `scripts/measure_map_extract.py`)
*Claims tagged [V] verified / [I] inferred in the file. Note: the extractor mis-indexes the first key block; that table was built by hand.*
- `0x50e41a0` (ImportAvatarMeasurement glue) = avatar import worker `0x50e3fc0` then CSV apply worker `0x50e4d80`. So `ImportAvatarMeasurement` works in a normal GUI session, while the 1-arg `ImportMeasurement(csv)` returns false unless CLO runs `headless`.
- **CSV format (from the parser):** line 1 read and discarded; line 2 read with delimiters `(` `)`: text between them is the unit, text before `(` ignored; every later row split on `,`, fields 1+2 form key `Name_Type`, field 3 parsed with `stod`. Unknown keys silently skipped; lookup is case-sensitive and exact. The line-1/2 layout is inferred from the parser alone (no CLO-written sample found).
- The repo's `measurement_template_unconfirmed.csv` (a wide single row) does **not** parse here; it fails with "Avatar size needs total height."
- **Units:** accepted strings exactly `m`, `feet`, `inch`, `cm`, `mm` (lowercase); anything else silently falls back to metres. Converted to cm internally (factors at `0x625bda0`). No half-girth handling: key names say "Circumference".
- **Key table:** 41 key strings in .rdata `0x89104c0..0x8910850` (initializer order, not index order), `Name_Type` with Type = Height | Circumference | Length; per-avatar hash map built in constructors `0x508a1f0`/`0x508b3f0`, lookup `0x50d9250`; indices up to 59 inside a 67-slot float array. Full name -> index -> unit table: section 2.3 of the file. Indices 0, 2, 6, 8, 26, 36 match lane C/F.
- **Required fields:** Total Height (idx 0) always; Bust (idx 2) for male, Under Bust (idx 5) for female. Gender comes from the avatar template name via `0x50d3680`. Missing required field -> log + false.
- **Application:** values go into a global size-manager singleton (`0xa320338`, 0x86B80 bytes) in a two-pass solve (dependent measurements recomputed, matching the ~50 derived floats that change), each clamped to 0.1-300 cm, then `0x50a0f70` applies the size to the avatar (same path as the GUI size panel). **Mesh re-deformation is inferred, not read from the kernels** (`0x513f190`, `0x51945e0`, `0x5146a40`, `0x5148d70`, `0x51449e0`, `0x516bcf0`). The importer does not touch `.avs` presets.
- `ExportAVT` worker `0x60a42f0`: forces `.avt` extension, exports the manager's *current* avatar (no index parameter), returns "" + logs "No AVT data available." if no avatar or any of three avatar flags (+0x618, +0x6A0, +0x6A8) set, then calls serializer `0x511f4f0`.
- Unknown: how the `.avt` header/ZIP fields are written (`0x3a03bf0` and below), inner workings of `0x50e3fc0`, the rule `0x50d1640` uses to pick the "current" avatar, and whether 336-written `.avt` hold 57 or 67 feature floats (lane F says 67 in `.dan`).

### Lane BC - container reader (`findings/51_container_reader.md`; `scripts/disasm_fn22.py`, `scripts/scan22.py`; raw `z22_*.txt`)
*Resolves the open "does CLO verify the digest / ZIP length on load" question from lanes C, Z, AV and BB. Static analysis.*
- **Reader = `MVFile::ReadHeader` at `0x3c277a0`** (called from the MVFile constructor chain `0x3ba17a0`); it picks one of two header readers by the byte at obj+0x34C: `0x3be2970` (QFile) or `0x3be3460` (FILE* "rb"). Import entry `0x6260840` (strings "[Not exist]", "[isOpen fail]", "[old version file]"). Magic check `0x3be13c0` loops over the 55 kinds, builds each magic from the table (`0x3ba1a70`, rdata `0x884c128`), compares 16 bytes and stores the matching kind in obj+0x2F0 (the kind comes from the file, not the caller). On mismatch obj+0x318 stays 0 and `0x6260840` fails with "[old version file]".
- Header u32s are read in order into obj+0x1C..0x30 (file offsets 0x10-0x24): file 0x20 -> obj+0x2C (ZIP offset), file 0x24 -> obj+0x30 (ZIP length).
- **The digest is NOT verified on load [V].** Callers of the hash helper `0x3bcdbd0`: `0x3be33d3` and `0x3be3e8b` (the two readers), `0x3bf516f` and `0x3c386f2` (the writers), `0x3c2415d` (key building); the salt string has one xref, inside the helper (`0x3bcdbf3`). For ver >= 11 the readers seek to obj+0x1B8 (digest record = zip_off-68), read the stored 64-hex string into obj+0x2D0, recompute SHA-256 over `file[0:obj+0x1B8]` plus salt into obj+0x358 and set obj+0x318=1, but never compare the two. The only compare is `0x3bbcb10` (0 = match, 1 = mismatch, 2 = bad header), called only from `0x6085c37` and `0x6086581` (two UtilityAPI functions that build a JSON-style `isValid` true/false result); `0x6260840` never calls it. So a digest mismatch causes no reject, warning or log on load; only the `isValid` query reports false.
- **ZIP offset/length:** `0x6260840` branches on obj+0x1C0, set only for ver >= 13 files, so our v11/v12 files take the zero branch (`0x3bd1220`): seek to obj+0x2C (file 0x20, trusted blindly), read obj+0x30 (file 0x24) bytes into a buffer (if 0x24 is 0 it uses filesize minus ZIP offset), write that buffer to a temp file for unzipping; the read's return value is not checked. Consequences: **a 0x24 larger than the real ZIP loads fine** (short read, zero tail) - this explains the -600 to -610 byte stale 0x24 in every pipeline-patched `.avt`; **a 0x24 smaller than the real ZIP truncates the ZIP, drops the end-of-central-directory record and breaks the load** (if a patched ZIP ever grows past the base ZIP, 0x24 must be raised). The ver >= 13 branch (`0x3bcc0e0`) seeks to obj+0x2C and copies a u64 length from obj+0x1C8 in chunks and fails on any short read. A separate whole-file route (`0x3bd0d90` -> `0x4b6e390`) opens the path as a ZIP and uses no header offsets (finds the central directory from the end of the file).
- **Implications:** editing header bytes (0x24, timestamps) does not need a digest recompute for the file to load; recompute only to keep `isValid` true. Never shrink 0x24 below the real ZIP size (`avt_patch_tool.py` sets it exactly). This lowers cause 7 in `findings/50` to very unlikely.
- Open [I]: where ver >= 13 files come from (finding 31 says the writer emits 12); that the ZIP library tolerates trailing zeros after the end-of-central-directory record is inferred from the empirical loads, not from `0x4b6e390`'s internals; the UtilityAPI names behind `0x60857e0` / `0x6086300` were not looked up.
