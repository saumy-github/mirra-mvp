# Modal dialogs and blocking risks (lane X: closes lane R open items)

*Status: static disassembly only (dumpbin + stdlib Python), CLO_Standalone_OnlineAuth_x64.exe 2026.1.336. Nothing was run or hooked.*
*Date: 2026-10-29*
*Tooling: `scripts/disasm_fn9.py` (copy of disasm_fn6, cache `raw/disasm9/`), `scripts/xref_dialog9.py <regex>` (string -> referencing function), `scripts/reach9.py <depth> <rva>...` (direct E8/E9 call reachability to dialog sinks; virtual calls NOT followed).*

Tags: **[V]** visible in listing/data, **[I]** inference. Addresses are RVAs (VA = 0x140000000 + RVA).

## 1. PreCheck 0x5cbb700 (the "Buttons with negative thread lengths" box)

Pseudo-code, verified from the full listing (183 instructions):

```
bool PreCheck():                               // 0x5cbb700 ; called only from SimStartStop 0x5cbfb40 when start==true
    scene = sharedptr copy of Scene holder (0x1be0dc0 -> 0x5cba300)
    if (0x1c09670(scene) /* = (scene.ptr == nullptr) */) return 0   // no scene: proceed silently
    list = 0x5cfe9f0(0x1bf5e20())  ->  0x4d34050(*list)           // vector<shared_ptr<Obj>> (16-byte elements) of scene objects
    for each obj in list:
        if (0x4749c70(obj) /* type test: "is a button-like object" */ ) {
            if (obj->vtbl[+0x910]() == 0) goto ASK        // per-object predicate FALSE => problem
        }   // elements failing the type test are skipped
    return 0                                       // nothing offending: proceed
ASK:
    r = 0x4b78650(text="Buttons with negative thread lengths may cause Simulation to be unstable. Would you like to proceed?",
                  buttons=6, title=<QString>, parent=-1)
    return (r == 1) ? 1 : 0
```
* [V] The box appears **only if** the scene exists AND at least one object passes the 0x4749c70 type test AND its `vtbl[+0x910]` returns false. Note the sense: `vtbl+0x910` true = OK. Lane R's name "negative thread length" is the dialog text; the predicate semantics (true = thread length valid) is **[I]**, deduced from the branch (false -> dialog) and the string.
* [V] Return value use, in 0x5cbfb40: `call 0x5cbb700; test al,al; jne exit` (0x145CBFB72-79). **Return 1 aborts the start; return 0 lets Simulate proceed.**
* [I] Since the text asks "Would you like to proceed?", button id `1` must be the "No"/cancel of button-set 6 (and Yes -> id != 1 -> proceed). The mapping of dialog-service ids was not decoded; if it were inverted, Yes would cancel. Treat both outcomes as untested.
* [V] **Reachable from Simulate with no buttons in the scene? No.** With an empty scene (`scene.ptr==0`) it returns 0 at once; with a scene but zero button objects the loop never reaches the vtable predicate. The reachability path exists statically: 0x607f070 -> 0x5cbfb40 -> 0x5cbb700 -> 0x4b78650 (reach9, depth 3).
* [V] The box is **not** the only start-time risk: when Simulate stops, nothing prompts. Start of simulation is where all pre-check prompts live.
* Mitigation: before `Simulate`, the plugin cannot read button thread lengths via the public API; the practical guard is to simulate only garments generated by Mirra's own pipeline (no Button objects), and wrap the call with a watchdog (section 7).

## 2. SRW lock + condition variable in 0x70d98d8 / 0x70d986c: **not a solver wait**

* [V] 0x70d98d8 is the MSVC CRT `_Init_thread_header` and 0x70d986c is `_Init_thread_footer` (thread-safe local-static initialisation, "Magic statics"). Evidence: header does `AcquireSRWLockExclusive(0xa35ea18)`; if guard `[rbx]==0` it sets it to -1 and returns to the caller to run the initialiser; if the guard is `-1` it calls `SleepConditionVariableSRW(cv=0xa35ea10, srw=0xa35ea18, INFINITE(-1), 0)` in a loop; otherwise it records the thread's epoch in TLS (`gs:[58h]`, +0xB8B8). Footer: lock, `++_Init_global_epoch (0xa172d8c)`, stores the epoch into the guard, `ReleaseSRWLockExclusive`, `WakeAllConditionVariable(0xa35ea10)` (IAT 0x822bb10). IAT names resolved with `iat_name.py`.
* [V] Example user: 0x1bc26d0 above (dialog-manager singleton), `0x1c23080` Sim::Instance, etc. All singleton accessors follow this pattern.
* So Simulate **does not wait on a worker thread join or a solver thread** through these helpers. They can block only if **another thread is in the middle of initialising the same function-local static** (the waiter sleeps until that thread's footer wakes it). On the single UI thread this can only deadlock if a static initialiser re-enters itself (recursive init on the same thread) or throws, leaving the guard at -1 [I]. Not expected in normal use.
* Solver worker pools: the per-frame code (section 3) calls 0x3a29c60 -> 0x3a5f820, which is a **vector<0xD0-byte element> destructor** (loops `vtbl[0](elem,0)`, element stride 0xD0, frees storage), not a join; and 0x6739ac0 is a bare `ret`. Both are local-variable destructors [V]. No `WaitFor*`/thread-join is visible in 0x5cbfda0 at first level [V]; deeper solver internals (called through virtual calls) are not followed [I].
* Conclusion: **Simulate cannot block indefinitely through the condvar in normal operation**; it blocks only through (a) the modal boxes in this file, and (b) the length of the loop itself (`steps` x frame cost).

## 3. Per-frame step 0x5cbfda0 (called from MVTimer_Update 0x5cc1da0)

Signature (inferred): `void Frame(MVTimer* t /*rcx*/, double dt /*rdx*/)`. Timer fields: `+0x34` byte "arrangement phase running", `+0x38` uint "phase frame counter" [V]. The source line asserted at entry is `MVTimer.cpp` line 0x75 (117): `0x4b7bd50(scene_exists, "...Simulation\\MVTimer.cpp", 0x75)` where `scene_exists = 0x1c097f0(scene)` (non-null). **If the scene pointer is null at that point the assert raises the "unexpected error E11000" box** [V] (cannot happen when Simulate is reached normally with the scene present; Simulate itself does not check).

Loop structure, reconstructed [V] unless marked:
```
Frame(t, dt):
  assert(scene != null)                                           // 0x145CBFDF6
  if (t->+0x34 == 0) {                                            // not currently in Folding/Draping
      // start the phase only if the scene is armed:
      if (scene && 0x3f3fae0(scene) /* some object in scene->+0x250 list qualifies */ && 0x3f2b7f0()->+0x9c != 3)
           { t->+0x34 = 1; t->+0x38 = 0; }
  }
  0x5cba340(Sim state, dt) ... (snapshot)
  if (t->+0x34 == 0) goto NORMAL_STEP (0xAD4)
  // --- phase running ---
  // choose which phases exist:
  if (t->+0x38 == 0)  fold = scene && 0x3f39a60(scene);           // list at scene+0x800 has an item needing fold
  else fold = 0;
  if (fold) 0x3f00290(scene)  /* begin folding */, nFold = 10
  else      nFold = (scene && 0x3f39550(scene)) ? 10 : 0
  total = nFold + 40                                              // r12d = rdi+0x28 -> 50 or 40
  if (solver && t->+0x38 < nFold) {      // FOLDING: counter 0..nFold-1  (10 frames)
      fold-step (0x3f67e70, once per frame, uses 0x3f3fab0 result as flag)
      if (!0x5cc4550()) goto END_NO_STEP            // GPU health check, see section 5
      progress("Folding", t->+0x38*100/total)       // 0x895f5a0 via UI delegate 0x1be0fc0 -> 0x6155870
      ++t->+0x38
  } else if (t->+0x38 >= total) {        // END: phase over
      0x3f47940(scene)  /* finish arrangement for each object in scene->+0x250 */
      t->+0x34 = 0                       // 0x145CC0ABE
  } else {                               // DRAPING: counter nFold..total-1  (40 frames)
      if (counter == nFold && nFold) 0x3f62310(scene)   // fold -> drape transition
      drape-step (0x3f67e70)
      if (!0x5cc4550()) goto END_NO_STEP
      progress("Draping", t->+0x38*100/total)           // 0x895f5a8
      ++t->+0x38
  }
  return                                 // NOTE: no normal solver step on phase frames
NORMAL_STEP (t->+0x34 == 0):
  0x3f392e0(scene) / 0x3f47940 / 0x3f3fab0 / 0x3f67e70 (dl=1)   // ordinary frame step on the solver
  if (0x5cc4550()) { 0x5cbdff0(SimState, dt, ...) ; if (flag) 0x4fcd750(...) ; 0x5cc4550() }   // advance sim time, 2nd health check
```
Conclusions [V]/[I]:
* "Folding" and "Draping" are **status-bar progress labels** (QString from `QObject::tr`, shown through `0x1be0fc0` -> `0x6155870` with a percentage), **not separate API modes**. They are an automatic **arrangement phase of at most 50 frames (40 when no fold is needed)** at the *start* of a simulation run: the first 10 frames "Folding" (only if the scene has a foldable/arranged item), then 40 frames "Draping". After `total` frames the phase ends (`+0x34=0`) and later frames are ordinary solver steps. [V] code; [I] interpretation as garment arrangement/pre-drape.
* A `Simulate(steps)` whose `steps` is below 50 may therefore spend **all its frames inside the Folding/Draping phase** and never reach an ordinary solver step; and because the counter lives in the MVTimer, **each Simulate call starts a new phase when SimStartStop re-arms `+0x34`** only if `+0x34` was cleared (it is cleared on stop, `0x5cbfd42`: `MVTimer->+0x34 = 0`). So each separate `Simulate` call re-runs Folding/Draping from frame 0 if the arming condition holds. Plugin implication: chunking Simulate into 25-50 step requests (lane R advice) **restarts the arrangement phase on every chunk**; prefer one call with a bounded larger `steps`, or verify empirically. [I]
* Early exits: (a) `0x5cc4550()==0` (GPU failure) returns without advancing; (b) `+0x38 >= total` ends the phase; (c) no solver / no scene (`[r15+0x34]==0` paths) skip. **No wall-clock timeout and no cancel flag** [V]. Total work is bounded by `steps` x frame cost.

## 7. Mitigation advice for the plugin (RestPlugin_windows.cpp)

1. **Watchdog on every modal-capable call.** Run `Simulate`, `ImportFile`, `ImportDXF`, `DisplayMessageBox` on the UI thread (as now) but start a timer thread beforehand; if the call has not returned after N seconds, find top-level windows of the CLO process with class `Qt*QWindow`/`#32770` and a QMessageBox-style title (`EnumWindows` + `GetWindowThreadProcessId`) and post `WM_CLOSE` / `BM_CLICK` on the default "No/Cancel" button, then log the box text (`GetWindowText` of the static child). Never call from the HTTP thread (lane R advice stands).
2. **Do not call `Simulate` on a scene with buttons**; Mirra's generated garments have none. Given the unknown button-id mapping, if a box ever appears prefer clicking the box's affirmative ("Yes") only after confirming it is this exact text.
3. **Avoid GPU simulation mode** (the sim property selects it, `0x3f33020()==1`): it adds two modal failure boxes (out of memory / error code). CPU simulation has neither.
4. **Do not rely on chunking `Simulate` to stay responsive**: each call restarts the 50-frame Folding/Draping phase when armed (section 3). Use one bounded call (e.g. 100-200 steps) protected by the watchdog, and compare cloth state before/after.
5. **Before ImportFile of a motion / graded-avatar / unknown-extension file**, validate extension and content in the REST layer; never import `.zip` or motion files unattended.
6. **Keep >10 GB free disk** on the CLO profile/temp volume to avoid the "insufficient memory space" prompt on save/load.
7. **Avatar resize/measurement apply**: make sure the avatar's Softbody and Divide options are off before resizing, or the two "Do you want to proceed?" boxes (0x82972a0 / 0x8459770, function 0x50a8710) can block `apply-measurements`. Check by exporting the avatar's option state or by setting them off in the base `.avt/.avs`.
8. **NewProject is safe** (no unsaved-changes prompt in the static path); keep `NewProject` before `clear-avatars` as now.
9. Treat `Simulate`'s `true` as "returned", never "succeeded"; the GPU-failure path stops the sim, shows a box and still returns `true`.
