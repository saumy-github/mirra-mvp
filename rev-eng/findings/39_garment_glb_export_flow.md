# 39 - Garment-only glTF/GLB export flow (lane AK)

*Status: static disassembly + GLB data check, 2026-10-29. Not run against CLO. Tags: [V] verified in disassembly/data, [I] inferred.*
*Scripts: `scripts/disasm_fn16.py` (copy of disasm_fn.py, cache `raw/disasm16/`), `scripts/ak_garment_probe.py`. Raw: `raw/ak_*.txt`.*

## 0. Call chain (corrects/extends findings 11 and 25)
ExportGLTF/GLB wrapper -> worker **0x60a5090** (this, out, path, mode=0, opt, bGLB):
1. [V] no document (`App[0x30]==0`) -> empty vector.
2. [V] all four lists (`+0xC8/+0xE0/+0xF8/+0x110`) empty -> `App[0x38]->vtbl[19]` = **0x1d8a6d0** (CLOFileIOImpl slot 19, vtable 0x8294390). Slot 19 tests `mode==1` (GUI path, shows the export dialog via QDialog::exec -> 0x5d6e520 on the dialog's options) else (mode 0 = API path, our case) calls **0x5d6eed0**(out, path, opt, bGLB). Fabric export (`opt+0x4C bExportFabric`) is a separate branch in slot 19 (string "Export Fabric (GLTF/GLB)").
3. [V] any list non-empty -> selection path: resolver **0x6099710** (lists -> std::set<uint> of object uids), empty set -> return empty vector; else copy opt into an internal option object (ctor 0x5c2b840, copy-assign 0x5c2d830), set uid list (0x1dda4b0), `0x5cabcf0` rebuild selection, then `CLOFileIOImpl slot 18` (0x1d8a6a0) -> **0x5d6e520**(out, path, internal_opt, bGLB).
4. 0x5d6eed0 (API whole-scene) [V]: allocates internal option (0x298 bytes, ctor 0x5c2b840), copies public opt (0x2da1050), applies bThin (see 1), `0x5cabc90` fills the selection by flags (below), `0x5c2fb20` prunes expired entries, then calls the same **0x5d6e520**. So both routes converge on 0x5d6e520 -> real writer **0x3d06cf0** (strings "Exporting glb"/"Exporting gl.."/"Exporting VRM").

The internal option = the public ImportExportOption layout up to 0x128 (offsets +0x43 bSaveColorWays, +0x44 bSaveInZip, +0x4C bExportFabric, +0x4D bSaveColorWaysSingleFile verified against the worker's uses) plus extra members: `+0xC6` (selection-filter active), `+0x230/+0x238` selection vector of 16-byte shared_ptr/weak entries, `+0x295` (byte set by 0x5ca7700, format).

## 1. What a garment-only export writes (bExportAvatar=false, bExportGarment=true)
- [V] 0x5cabc90: `if opt[+8] bExportGarment: 0x5cb2980(sel,0)`; `if opt[+9] bExportAvatar: 0x5cb2520(sel)` (this one references avatar GUIDs and statics); `if opt[+0x58] (bIncludeSceneProp, default true): 0x5cb3450`. So bExportAvatar=false drops all avatar meshes, skeleton and skins. Garment selection (0x5cb2980) reads `bIncludeHiddenObject` (+0x2B, 3 uses): default false -> hidden garment objects are skipped.
- [V, data] What the garment contributes (existing `clo_vto/output/u_015/c_004/s_001/001/simulation.glb`, CLO 2026.1.224): the draped **3D garment**, not 2D patterns. Node `Cloth` -> 4 mesh nodes (names "1","2","3","7" = pattern/piece names), each 1 primitive with only POSITION/NORMAL/TEXCOORD_0 (no JOINTS/WEIGHTS: unskinned, rigid world-space mesh at the simulated drape). Counts: 1626 / 1717 / 401 / 406 vertices, 3118 / 3306 / 737 / 747 triangles = ~10.4k triangles total. These counts are single-layer (thin mesh): front and back panels are separate pieces, no inner offset shell. One shared material for all four pieces.
- [V] `bThin` (+0x10, default true): in 0x5d6eed0 the option is compared with the global thin/thick mode (`0x3f2b7f0()+0x94`); if different, the global mode is switched with 0x3f68880 for the export and restored afterwards. So bThin=true gives the single-layer cloth mesh seen above; bThin=false would export thick mesh (two offset shells, more vertices) [I, not run].
- [I] Seam puckers: they are in the simulated particle positions, so they are exported as-is; no smoothing in the exporter. `weldType` (+0x0C) is the only vertex-merge control; finding 25 saw no visible effect on the avatar, so assume the same for cloth (default FULLY_UNWELDED but output was not triangle-unwelded: 1 glTF vertex = 1 render vertex). Not tested.
- [I] Buttons/graphics/zippers: only come in when selected via the lists or when the whole-scene selection (0x5cb2980) collects them; the u_015 file has no separate button meshes (all 4 meshes share material 0), garment has none. Button/trim meshes would show as extra mesh nodes under `Cloth` with their own materials.
- [V] `bIncludeInnerShape` (+0x2C, default false) not exported (internal lines).

## 2. Component filter resolution (0x6099710)
Signature: (scene_ptr, tmp, &patternList, &buttonList, &graphicList, &zipperList, &out_set<uint>) [V from arg setup in 0x60a5090].
- patternList (`vector<int>`) [V]: for each index: skip if `idx < 0` or `idx >= (scene.list_end - scene.list_begin)/16` (list at `[scene+8..+0x10]`, 16-byte shared_ptr entries) or the entry is expired (0x1c098a0 lock fails). Valid entries insert `entry->[+0x10]` (uid) into the output set (dedup). So invalid/negative/out-of-range ids are **silently ignored**, never an error; duplicates collapse. [I] The scene list is the same ordering as RealPatternList/PatternAPI (0-based); the code only proves it is a 16-byte-element pointer list.
- buttonList, graphicList (`vector<unsigned>`) [V]: uids are inserted into the set without any validity check (insert-if-absent). Stale uids therefore make the set non-empty, and only fail later when no object matches.
- zipperList [V]: each uid looked up in a map (0x3b84e70); found zippers expand to their tape+hardware uids (matches finding 08 text); unknown uid is skipped.
- Empty resolved set -> **empty vector returned, no file written** [V, 0x60a5090 `cmp rbx,[rsp+58h]; jne` else call 0x666b740 (clear)]. Then, even with a non-empty set, 0x5d6e520 returns an empty vector if its selection vector (`+0x230`) is empty and bExportFabric==0 [V: `cmp [r13+230h],[r13+238h]; jne; cmp byte [r13+4Ch],0; je ret`]. So a stale-uid-only selection also yields `[]`.
- Mixed valid/invalid ids: the valid ones are exported, invalid ones dropped, no error or log to the caller [V for patterns; I for buttons].
- Return value [V]: `vector<string>`: `[main file]` followed by the auxiliary-file vector produced by writer 0x3d06cf0 (second out-vector, 0x5d6e520 appends both). For `bSaveInZip` (+0x44) the output is replaced by a single `<name>zip` archive name (0x5d6e520 builds it via 0x4b6a260 and the literal "zip") [I: exact name]. For bSaveColorWays (+0x43)=1, colorways>1 and bSaveColorWaysSingleFile(+0x4D)=0 it loops over colorways and writes one file per colorway (names `<path>_<colorway>` style, 0x5d6e520 lines at 0x145d6e832-0x145d6ea3c) [V loop, I naming].
- GLB: extension `glb` / glTF: `gltf` forced onto the name when zipping (literals 0x82910EC "glb", 0x8333274 "gltf") and the main path gets `.glb` (0x883a580) or `.gltf` (0x883a588) appended in the colorway branch [V]. Safe practice: pass a path ending in `.glb`.
- Textures [V data]: in the GLB all 27 images are **embedded** in the BIN chunk (bufferViews, image/png + image/jpeg); no sidecar files in `u_015/.../001/` except `simulation_Default Colorway.png` (a CLO thumbnail from another call). For `ExportGLTF(...,false)` expect `.gltf` + `.bin` + image files in the same folder [I], unless `bEmbedded` (+0x4A) is set.

## 3. Units, axes, alignment
- [V, data] Y-up, metres: combined GLB bounds X +-0.44, Y -0.013..1.908, Z -0.18..0.16 with plugin `scale=0.001` (finding 25). Garment pieces sit at Y 0.92..1.62 (torso), X +-0.37, i.e. in the same frame as the body.
- [V] axisX/Y/Z (+0x34/+0x38/+0x3C default 0/1/2) and bInvertX/Y/Z are identity by default; finding 08 says "no conversion". The CLO world frame is already Y-up, so no extra axis flip appears in the data. Unit conversion is only the multiplicative `scale` (+0x30, plugin value 0.001; default 1.0 would give mm) [V data, writer-internals not traced: 0x3d06cf0 deeper not followed].
- [V, data] Node `Cloth` (4 meshes) and the avatar root `MV2.1_Jinho` are siblings under `simulation_Scene_Node`; the garment meshes have **no node transform** (world-space vertices), avatar has bone transforms (root Joint translation Y=1.085 m). So garment and avatar share one frame in a combined export.
- [I] Separate exports (avatar once, garment later): the exporter has no recentring/auto-translate step in the code traced (translationValue*, bAutoTranslate are import-only options per finding 08, and no use of them exists in 0x5d6e520/0x5d6eed0). Expect identical world frame as long as the avatar is not moved between exports and no `bAutoTranslate` happened after the avatar export. Verify by comparing the avatar GLB's body bounds with the garment's min/max (garment should lie inside the body's X/Y/Z extents).

## 4. Materials (from the existing GLB, writer code not traced)
- [V, data] Fabric material (`FABRIC 1_2411138`): `pbrMetallicRoughness {baseColorFactor [0.041,0.018,0.014,1], baseColorTexture (index 0), metallicFactor 0.0, roughnessFactor 0.5}`, `KHR_materials_specular {specularFactor 0.15}`, `doubleSided: true`, **`alphaMode: "BLEND"`** although baseColorFactor alpha = 1, `KHR_texture_transform` on the baseColorTexture with `scale [0.0065, 0.00897]` (tiles the fabric swatch), listed in `extensionsRequired`. So the viewer must support KHR_texture_transform; three.js GLTFLoader does. No normalMap and no metallicRoughnessTexture on the fabric material (avatar materials do have metallicRoughnessTexture). `bCreateMetallicRoughnessMap` (default false) and unified-texture bake flags (default false) were off in this export; with unified UV flags false the textures are the original fabric swatches with UV tiling via KHR_texture_transform, not a baked atlas [I].
- [I] baseColorFactor multiplies the texture (glTF spec): the factor [0.04,0.02,0.01] looks like a dark base multiplied by the swatch; check in the viewer that colours are not double-darkened (CLO uses factor=fabric colour when texture is a pattern swatch tint).
- [I] `BLEND` for opaque cloth causes sort/transparency artefacts in three.js: viewer should force `material.transparent=false; alphaTest or opaque` unless the texture has real alpha. `bOpacityMap` (+0x47) controls the opacity map generation from diffuse alpha (default false).
- Texture size/format [V data]: PNG or JPEG as stored in the zprj (no resampling flag found); sizes depend on the source swatch, unified-texture size default 2048 px only applies when `bUnifiedUVCoordinates`/bClothUnifiedUVCoordinates are set.

## 5. Recipe for the plugin (garment-only try-on viewer)
1. Simulate (no modal; see finding 29), wait for Simulate to return.
2. Avatar once: ExportGLB with `bExportAvatar=true, bExportGarment=false, scale=0.001` (avatar GLB does not depend on garment; GLB is ~30 MB mostly textures and skin, finding 25).
3. Garment per try-on: `ExportGLB(path, opt)` with `bExportGarment=true, bExportAvatar=false, scale=0.001`, `bThin=true`, `bIncludeHiddenObject=false`, all four lists empty (whole-scene path 0x5d6eed0). Add `patternList` only to drop specific pieces; otherwise keep it empty to avoid the stale-index -> empty-vector pitfall.
4. Keep `bSaveColorWays=false` (default), `bSaveInZip=false`, `bEmbedded` irrelevant for GLB.
5. After: result vector length >= 1; first entry exists on disk, size > 0; parse JSON chunk, expect `meshes` named after pieces with no `skins`; `python -I scripts/glb_probe.py summary <file>`: expect verts ~1-2k per piece (thin mesh), skins 0, images embedded. Compare garment min/max with the avatar's body bounds (same Y-up metres frame).
6. If the returned vector is empty: either no document loaded, list resolved to nothing, or nothing selected (garment hidden, no cloth in scene). It is not an error code; check the CLO log.
7. Viewer: load both GLBs in one scene without extra transforms; enable KHR_texture_transform; set cloth material `transparent=false`, `side=DoubleSide`.
