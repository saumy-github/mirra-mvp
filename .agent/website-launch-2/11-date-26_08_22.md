# 11 — 2026-08-22: the DNS/Atlas problem, today's workaround, and the architecture fix it points to

**Written**: 2026-08-22.
**Today's action**: switch `MONGODB_URI` from the `mongodb+srv://` form to the direct (non-SRV) form. User does this — no agent reads or writes `.env` files.
**Longer term**: doc `08` Concern 11 — only the backend talks to MongoDB.

---

## 1. The problem in one line

**The router at `192.168.0.1` cannot deliver any DNS answer larger than 512 bytes, and `mongodb+srv://` needs one.**

Everything else on this machine works because nothing else asks a question that big.

## 2. Why it never happened on any previous project

DNS answers travel in one small packet — a hard 512-byte limit set decades ago. Ordinary lookups are nowhere near it. Measured on this machine, 2026-08-22:

```
A    api.stripe.com     ->   64 bytes    fits
A    mongodb.net        ->  110 bytes    fits
A    google.com         ->  124 bytes    fits
```

Every REST API, auth provider, and database host resolves to a handful of IP addresses. That is every project built here before this one — small answers, always delivered, no problem ever visible.

When an answer *is* too big, DNS has a standard plan: the server returns an empty response with a **truncated** flag, and the client re-asks over **TCP**, which has no size limit. Both halves measured:

```
google.com TXT, no EDNS   ->   28 bytes, truncated=True   ("too big — ask again over TCP")
google.com TXT, with EDNS -> 1103 bytes, 16 records       (the real answer)
```

**This router breaks all three routes at once:**

| Route | Result |
|---|---|
| Large answer over UDP | silently dropped |
| Bigger UDP buffer (EDNS) | not supported |
| Retry over TCP port 53 | **ConnectionRefused** |

So a large answer has no way home. Not slow — impossible. Proven:

```
A   google.com      (small, UDP)      OK    0.0s
A   api.stripe.com  (small, UDP)      OK    0.0s
TXT google.com      (large, UDP)      FAIL  6.4s  LifetimeTimeout
TXT google.com      (large, TCP)      FAIL  2.0s  ConnectionRefusedError
TXT google.com      (UDP, edns=512)   FAIL  6.0s  Timeout
```

**A misleading early data point, recorded so nobody repeats it**: a *small* SRV record resolved fine through this router, which made SRV look healthy and sent the first diagnosis down the wrong path. **Response size is what matters, not record type.**

## 3. What exactly needs so many bytes

`mongodb+srv://` does not ask for one address. It asks *"who are all the servers in this cluster, and how do I connect?"* — two queries, both large.

Verified against the live cluster, 2026-08-22:

```
topology    : replica set
replica set : atlas-tyjfm2-shard-0
members     : ac-aekbtq9-shard-00-00.qmprvla.mongodb.net:27017
              ac-aekbtq9-shard-00-01.qmprvla.mongodb.net:27017
              ac-aekbtq9-shard-00-02.qmprvla.mongodb.net:27017
primary     : ac-aekbtq9-shard-00-02.qmprvla.mongodb.net:27017
```

1. An **SRV** query returns all three hostnames, each ~42 characters, each with priority, weight and port.
2. A **TXT** query returns connection options (`authSource`, `replicaSet`, `retryWrites`).

Together with DNS overhead, that lands in the same range as the 1103-byte TXT measured above — **well past 512**.

### Correcting a natural assumption

**The three addresses are not our three components.** They are **Atlas's own replica-set members** — every Atlas cluster, free tier included, runs three nodes: one primary taking writes, two secondaries replicating it, so the cluster survives a node failure.

Backend, worker and `mirra_measurements` do not appear in DNS at all. They are **clients**. Each independently asks the same question and receives the same ~1000-byte answer.

**Consequence that matters: reducing the number of clients does not shrink the DNS response by one byte.** Ten clients or one, the answer is identical — it is a property of the cluster, not of who is asking.

## 4. Why Docker was never affected

| Component | Runs in | Resolver used | Atlas reachable |
|---|---|---|---|
| Backend | Docker | Docker's own (Linux VM) | **yes — never failed, all day 2026-08-20** |
| Worker | native Windows | the router | no |
| CLI pipeline | native Windows | the router | no |

Identical `MONGODB_URI` in all three. The only difference is **which resolver the process talks to**. This is why the backend reported `{"status":"ok","database":"connected"}` throughout a day in which the worker could not make a single connection.

## 5. Today's fix — the direct (non-SRV) connection string

Replace the `mongodb+srv://...` value with Atlas's direct form, which names the three hosts explicitly:

```
mongodb://<user>:<pass>@ac-aekbtq9-shard-00-00.qmprvla.mongodb.net:27017,ac-aekbtq9-shard-00-01.qmprvla.mongodb.net:27017,ac-aekbtq9-shard-00-02.qmprvla.mongodb.net:27017/?ssl=true&replicaSet=atlas-tyjfm2-shard-0&authSource=admin&retryWrites=true&w=majority
```

**Why this works**: no SRV lookup, no TXT lookup. Each hostname is a plain **A-record** lookup — the small kind this router serves fine. Everything else (TLS, auth, replica-set behaviour, failover) is unchanged; only how the driver *discovers* the hosts differs.

**Where it goes**: `worker/.env` and `mirra_measurements/.env` at minimum — the native processes that were failing. The backend works either way, but keeping all three identical avoids a future "why does only this one work" puzzle.

**Trade-off, stated honestly**: the SRV form exists so Atlas can change cluster topology without you editing anything. With the direct form, if Atlas ever moves or renames nodes, the string must be updated by hand. For a pilot on a fixed cluster this is a fair trade; it should not be forgotten if the cluster is ever resized or migrated.

**Not chosen: changing the machine's DNS.** `Set-DnsClientServerAddress -InterfaceIndex 7 -ServerAddresses 8.8.8.8,1.1.1.1` would also work, but it fixes the machine rather than the project — it silently reverted once already on 2026-08-20 when a VPN dropped, and it does nothing on any other network.

## 6. The architecture fix this points to — doc 08, Concern 11

The connection string fixes the *lookup*. Concern 11 fixes the *shape*, and today's evidence is the strongest argument for it yet.

**Only the backend should talk to MongoDB.** The worker runs CLO and reports results back through the backend; it holds no database credentials and opens no database connection.

This does not repair the router. **It removes the router from the critical path** — the only component doing Atlas DNS becomes the one already resolving correctly, inside Docker. The worker talks to the backend over `localhost`, which needs no DNS at all.

What today added to the case:

- Every failure on 2026-08-20 came from a **native process** doing its own Atlas lookup. The containerised backend never failed once.
- The worker is a native Windows process outside the container network. Giving it fewer external dependencies — and no database credentials — is sound independently of any DNS issue.
- The pipeline needs **measurements**, not a database connection. `step_03` already supports a JSON measurement file (`ctx.measurement_file_input`) and skips Mongo entirely when given one. Two of the three touchpoints are nearly free.

Full inventory of what changes, what gets deleted, and the four approaches considered: **doc 08, Concern 11**. The honest cost there is not the five endpoints — it is that **no service-to-service auth exists anywhere in the backend today**, so that has to be built.

**Sequencing**: the connection string is today. Concern 11 is a scheduled piece of work, not a same-day fix. They are complementary — the string unblocks now, Concern 11 makes it structurally irrelevant later. Neither makes the other pointless.

## 7. Status

- [x] Root cause identified and proven with measurements
- [x] Wrong theory (record *type* rather than *size*) recorded as wrong
- [ ] **User to switch `MONGODB_URI` to the direct form** — the one action for today
- [ ] Re-run the pipeline natively to confirm the worker reaches Atlas
- [ ] Concern 11 — scheduled separately, not today

# PART 2 — the avatar-doubling bug: root cause and fix plan

Written 2026-08-22, after the DNS fix unblocked native pipeline runs.

## 8. What was actually wrong (root-caused, not theorised)

Runs failed intermittently — 7 of 15 — at `step_11_save_outputs` with *"Saved avatar measurements did not fully match the requested AVT-backed targets."*

**The user spotted it from the CLO UI**: opening `result_project.zprj` from run 080 showed the avatar visibly doubled, with the Avatar dropdown reading `result_project_1`.

Confirmed by reading the saved projects directly:

```
u_001-075 (PASSED):  1 .avt member in the archive
u_001-078 (PASSED):  1 .avt member
u_001-080 (FAILED):  2 .avt members
u_001-076 (FAILED):  3 .avt members
```

**Passing runs have exactly one avatar in the project. Failing runs have more than one.** That is the entire correlation.

Reading the measurements inside each avatar of the failing projects:

```
u_001-080   requested 178.5 / 100 / 85
  result_project_0.avt   188.0 / 96.5 / 82.5   <- base            <- WE EXTRACT THIS
  result_project_1.avt   178.5 / 100  / 85     <- CORRECT

u_001-076   requested 165 / 92 / 76
  result_project_0.avt   178.5 / 100  / 85     <- run 075's body  <- WE EXTRACT THIS
  result_project_1.avt   188.0 / 96.5 / 82.5   <- base
  result_project_2.avt   165.0 / 92   / 76     <- CORRECT
```

**The correct avatar was present in the project every single time.** Measurement application was never broken — `step_08` worked on every run. We simply exported the wrong body out of a project that contained the right one.

### The two defects

**Defect A — we extract avatar 0 instead of the active one.** `step_11_save_outputs.py:34`, `_extract_project_artifacts()`:

```python
for member in archive.namelist():
    if suffix not in EXTRACTABLE_SUFFIXES or suffix in seen_suffixes:
        continue          # takes the FIRST .avt, then skips the rest
```

With one avatar this is correct. With several, avatar 0 is a leftover and the real one is last. **This is the defect that produced wrong output**, including run 076 exporting a *previous run's body* under a different user's run id.

**Defect B — avatars accumulate in the scene.** `new-project` does not remove them, so each run leaves its avatar behind for the next.

Fixing **A** alone makes every run correct. Fixing **B** removes the ambiguity at source. Both are worth doing; A is testable today with no plugin rebuild.

### Why nothing caught this earlier

- `step_09_readback` reports `achieved: null` for every field — the plugin *"does not expose resulting body measurements field-by-field"*. Steps 09 and 10 echo the requested values and verify nothing.
- `step_11`'s file comparison is **the only real check in the pipeline**. It must never be weakened to make runs pass.
- Identical test measurements hid it completely: when every run requests the same body, a stale avatar reads as a perfect match. Only varying the inputs exposed it.

## 9. Why `new-project` cannot clear avatars — confirmed from the SDK and the vendor changelog

The SDK is explicit (`UtilityAPIInterface.h:419-421`, in both 2025.2.368 and 2026.0.356):

```cpp
/// @fn NewProject()
/// @brief Clear the current garment and begin a new garment
virtual void NewProject() {}
```

**"Clear the current garment."** Avatars are not mentioned and are not cleared. We were relying on it to do something it never claimed to do.

### There is no Ctrl+N equivalent in the API

Searched the entire 2026.0.356 SDK for `NewGarment`, `ClearAll`, `ResetProject`, `InitProject`, `CloseProject`, `ClearScene`, `DeleteAll`. **`NewProject()` is the only match.** The File > New Project menu item does more than any single API call exposes.

The vendor changelog confirms the gap ([developer.clo3d.com/changelog.html](https://developer.clo3d.com/changelog.html)):

- **`DeleteAvatar` — added V8.0.0, April 2025**: *"Added support to delete one or more avatars via index. Accepts a list of avatar indices. Returns true on success, false otherwise."*
- **`NewProject` is not mentioned in the changelog at all.**
- **No scene-clearing or project-reset API is documented.**
- Nothing documents whether avatars persist across `NewProject` — the behaviour we established empirically is simply undocumented.

So matching Ctrl+N means composing it ourselves:

```
NewProject()                 // clears garments — already done
+ DeleteAvatar([indices])    // clears avatars — not yet exposed by our plugin
```

`DeleteAvatar` has been available since V8.0.0, so this was never blocked by the SDK. Our plugin simply never exposed it.

### One safety constraint that shapes the design

| Call | Header | Family | Risk |
|---|---|---|---|
| `DeleteAvatar` | `UtilityAPIInterface.h:1915` | **UTILITY_API** | safer family |
| `GetAvatarCount` | `ExportAPIInterface.h` | **EXPORT_API** | the family behind the original SEH crashes |
| `GetAvatarNameList` | `ExportAPIInterface.h` | **EXPORT_API** | same |

`EXPORT_API` is exactly the family implicated in `POST_MORTEM_v1.1.1.md`, and the reason `has_avatar_state_readback` is `false` today.

**Therefore: do not call `GetAvatarCount` to decide what to delete.** Delete a fixed generous index range and let out-of-range deletions fail harmlessly. That keeps the whole operation inside the safe family.

## 10. The plan

### Phase 1 — fix extraction (Python only, no rebuild, do this first)

`step_11_save_outputs.py`'s `_extract_project_artifacts()` must select the **active** avatar rather than the first.

- Prefer the **highest-numbered** `.avt` member (`result_project_N.avt`), which matched the UI's selected avatar in every case examined.
- Better if cheap: parse the selected-avatar name from the project and match it exactly, rather than relying on ordering.
- **Log how many `.avt` members the archive contained.** More than one means Defect B is still occurring, and that signal must stay visible after Phase 2 supposedly fixes it.

This alone should take the pass rate from ~50% to ~100% without touching CLO.

### Phase 2 — clear avatars properly (plugin change + rebuild)

Add a plugin command that composes the real "new project":

- New command, e.g. `clear-avatars`, calling `UTILITY_API->DeleteAvatar({0,1,2,...,7})`.
- Do **not** call `GetAvatarCount` — see the safety constraint above.
- Add `TraceLog` `BEGIN`/`END` around it, matching `import-avatar-avt`. Doc `09` §6.2 already argues this is the highest-value instrumentation available, and today's diagnosis only worked because the hung batch happened to hold exactly one command.
- Call it from `step_07` immediately after `new_project()`.

**Before rebuilding, review doc `09` §3b** — the rebuild also ships `DoFunctionAfterLoadingCLOFile`, a callback firing on every file load that has never run in production. Add a `TraceLog` line at its top so a reentrancy hang is distinguishable from other failures.

### Phase 3 — verification, using the new test users

Five users seeded into `measurements` on 2026-08-22 via `mirra_measurements/seed_test_users.py` (separate from `seed_measurements.py`, so re-running never disturbs the golden users):

|---|---|---|---|---|---|---|---|
| u_011 | 168.0 | 62.0 | 92.0 | 76.0 | 92.0 | 79.0 | 42.0 |
| u_012 | 175.0 | 72.0 | 98.0 | 82.0 | 96.0 | 83.0 | 44.5 |
| u_013 | 181.0 | 88.0 | 106.0 | 92.0 | 104.0 | 86.0 | 47.0 |

All male, all seven pipeline-required fields present and in range. Deliberately distinct bodies so a swapped avatar is unmistakable. **`u_014` and `u_015` share a height of 186.0 on purpose** — height alone cannot distinguish them, but chest (100 vs 112) and waist (84 vs 98) can, which catches a swap a height-only check would miss.

Test protocol:

### What NOT to do

- **Do not weaken `step_11`'s verification to make runs pass.** It is the only real check in the pipeline, and the one thing standing between a user and another user's body.
- **Do not call `GetAvatarCount`** to size the delete list — `EXPORT_API`, crash-prone family.
- **Do not skip `new-project`.** It still clears garments, which matters once patterns enter the picture.

# PART 3 — making single-avatar guaranteed, not hoped for

Design decision by the user, 2026-08-22: **the scene must contain exactly one avatar at all times, and we verify index 2 is empty to prove it.** This section works out how to do that safely and what else is needed to make it genuinely foolproof.

## 12. The probes we can safely use

The constraint from §9 stands: `GetAvatarCount` and `GetAvatarNameList` live in `ExportAPIInterface` — the family behind the original SEH crashes, and the reason `has_avatar_state_readback` is `false`. **They stay off-limits.**

But `UtilityAPIInterface` — the safe family — has probes that answer the same question per index:

| Call | Line | Returns | Use |
|---|---|---|---|
| `IsShowAvatar(int index)` | 580 | `bool` — *"if avatar is shown, return true. if avatar is hidden, return false."* | cheap existence probe |
| `GetAvatarProperties(uint index)` | 2626 | `map<string,string>` of properties (`DivideMesh`, `KineticFriction`, `SkinOffsetMM`, …) | richer probe — an **empty map** means no avatar at that index |
| `DeleteAvatar(vector<int>)` | 1915 | `bool` | the delete itself |
| `SetAvatarActivation(name, bool)` | 2336 | `bool` | activate/deactivate by **name**, not index |

**This is the key finding for this design**: we can probe a specific index without ever calling the crash-prone counting APIs.

**One caveat to establish before relying on it.** `IsShowAvatar` returns `false` both for *"index 2 has a hidden avatar"* and *"index 2 has no avatar"* — the default body is `{ return false; }`, so a non-existent index and a hidden avatar are indistinguishable. `GetAvatarProperties` is the better probe: a populated map cannot be produced by a non-existent avatar. **Prefer `GetAvatarProperties`; treat a non-empty map as "an avatar exists here".**

## 13. The user's design, stated precisely

> "for deletion we have to make sure there is always a single avatar in the project, and we will check at the index 2 to make sure it is empty."

Concretely, in the plugin:

```
clear-avatars:
    DeleteAvatar({0,1,2,3,4,5,6,7})       // generous fixed range, no counting
    probe index 1 -> must be empty        // nothing survived
    probe index 2 -> must be empty        // the user's explicit check
    return { cleared: true/false, probe_1_empty, probe_2_empty }
```

Then after `import-avatar-avt`:

```
    probe index 0 -> must be NON-empty    // our avatar is there
    probe index 1 -> must be empty        // no doubling
    probe index 2 -> must be empty        // margin
```

**Why probing index 2 and not only index 1**: index 1 alone proves "not exactly two". Checking 2 as well gives a margin against a delete that partially succeeded, and against CLO reusing indexes in an order we do not control. It costs one extra call and closes a whole class of "nearly right" states. Good instinct — keep it.

**Why a fixed delete range rather than a counted one**: it avoids `GetAvatarCount` entirely. Deleting an index that does not exist should simply return `false`, which we ignore. **Verify that assumption on the first live test** — if a bad index throws or hangs instead of returning `false`, narrow the range and probe upward instead.

## 14. What else is needed to make it foolproof

The probes above verify CLO's *in-memory* state. That is necessary but not sufficient — the bug we actually shipped was in the **saved artifact**, not in the scene. Full-proofing means checking at every layer where the truth can diverge.

### 14.1 Check the saved project, not just the live scene — **the strongest check we have**

Counting `.avt` members inside `result_project.zprj` is:

- **Zero-risk** — pure Python, reads a zip, touches no CLO API.
- **Authoritative** — it inspects the artifact we actually ship, not a report about it.
- **Already proven** — it is exactly what root-caused this bug.

```python
avts = [m for m in zipfile.ZipFile(zprj).namelist() if m.lower().endswith('.avt')]
if len(avts) != 1:
    fail(f"expected exactly 1 avatar in project, found {len(avts)}: {avts}")
```

**This must be a hard failure, not a warning.** If CLO's probes say one avatar and the project contains two, the project is right and the probes are wrong.

### 14.2 Fail early, not at step 11

Probe the scene at the **start** of `step_07`, before importing anything. If avatars already exist, the previous run leaked — fail immediately rather than 60 seconds later at `step_11`. Cheap, and it attributes the failure to the run that caused it instead of the one that inherited it.

### 14.3 Verify the extracted avatar against the file we handed CLO

We already know exactly what we asked for: `clo_payload.patched.avt`. After extraction, compare it field-by-field with `result_avatar_from_project.avt`.

This is stronger than comparing against *requested values*, because it catches the case where CLO altered the body between import and save — a possibility no current check would notice. Both files are on disk; `read_field_values()` already exists.

### 14.4 Select by name, not by position

`SetAvatarActivation` works on **avatar name**, and the CLO UI showed `result_project_1` as the selected avatar. If the plugin can report the active avatar's name, `step_11` can extract *that* member instead of inferring from ordering. Position is a heuristic; name is the actual identity.

Worth doing even once single-avatar is guaranteed — it makes the extraction correct **by construction** rather than correct *because* the scene happens to be clean.

### 14.5 Keep the count in the run log, permanently

Log the `.avt` member count on every run, including successful ones. If Phase 2 regresses, the number climbs and we see it immediately instead of rediscovering it through wrong avatars months later.

### 14.6 Do not let a "fix" hide the signal

After Phase 1, extraction picks the right avatar even when several exist — which means **runs will pass while the scene is still dirty**. That is precisely how this bug would become invisible again. §14.1 and §14.5 exist to prevent that: correct output with `len(avts) != 1` must still fail the run.

### 14.7 A last-resort backstop worth naming

If probes and deletion prove unreliable in practice, the guaranteed-clean option is **restarting CLO between runs**. Expensive (~30-60 s) and unattractive for a queue, but it is the only method with no failure mode at all. Worth keeping in mind as the fallback if Phase 2 does not hold up — not as the first choice.

## 15. Ordering of the checks

```
step_07 start:
    1. probe idx 0,1,2      -> all empty, else FAIL EARLY        (14.2)
    2. new-project          -> clears garments
    3. clear-avatars        -> DeleteAvatar + probe 1,2 empty    (13)
    4. import patched .avt
    5. probe idx 0 non-empty, idx 1 and 2 empty                  (13)

step_11:
    6. save project
    7. count .avt members in zprj -> must be exactly 1, else FAIL (14.1, hard)
    8. extract by active name if available, else highest index    (14.4)
    9. compare extracted vs clo_payload.patched.avt               (14.3)
   10. compare extracted vs requested values                      (existing check — keep)
   11. log the member count regardless of outcome                 (14.5)
```

Steps 7, 9 and 10 are all Python-side and risk-free. Even if every CLO-side probe fails or is unavailable, **7 and 9 alone would have caught this bug on the very first failing run.**

# PART 4 — what actually fixed it: a race, not an API problem

Written 2026-08-23. **This part supersedes several conclusions in Parts 2 and 3 — read it before acting on them.**

## 17. The short version

The avatar accumulation was **a timing race, not a missing API**. `new-project` clears avatars perfectly well; it just needs CLO to have finished the previous run's work first. Nothing in the pipeline waited, so run N+1 called `new-project` roughly one second after run N exited, while CLO was still writing a 30-60 MB GLB.

The fix is a settle delay in `step_07`. Five back-to-back runs went from **3, 4, 1, 1, 2 avatars** to **1, 1, 1, 1, 1**, all with correct measurements.

**The hypothesis came from the user**, after two failed attempts at API-level fixes.

## 18. What was tried and what it cost

### Phase 1 — extraction fix (Python). WORKED, kept.

`_extract_project_artifacts()` now selects the **highest-numbered** `.avt` member rather than the first, via `_select_member()`. Replayed against every historical failure:

```
u_001-080: 2 avatars -> selects result_project_1.avt -> 178.5/100/85  MATCH (requested)
u_001-076: 3 avatars -> selects result_project_2.avt -> 165.0/92/76   MATCH
u_001-078: 1 avatar  -> selects result_project_0.avt -> 172.0/96/80   MATCH
```

This alone took the pass rate from ~50% to 100%. **It stays as the safety net** even now that the scene is clean — extraction is correct regardless of how many avatars are present.

### Phase 2 — `clear-avatars` plugin command. ABANDONED. Cost: three CLO crashes.

Every attempt to manage avatars through the API failed:

| Attempt | Result |
|---|---|
| `DeleteAvatar({0..7})` blind on a possibly-empty scene | **hung CLO** — `BEGIN clear-avatars` with no `END` |
| `GetAvatarProperties(0)` as an existence probe on an empty scene | **crashed the CLO process outright** |
| Count our own imports, delete `[0..n-1]` | **wrong premise** — the pipeline imports twice per run but the scene often holds one avatar, so `DeleteAvatar({0,1})` hit a non-existent index 1 and **hung** |

**Every route to knowing or changing avatar state is closed:**

| Approach | Status |
|---|---|
| `GetAvatarCount` / `GetAvatarNameList` | ExportAPI — excluded since the original SEH crashes |
| `GetAvatarProperties(i)` | **crashes** on an absent index (proven 2026-08-22) |
| `IsShowAvatar(i)` | cannot distinguish hidden from absent |
| `DeleteAvatar([...])` with any guessed range | **hangs** on an absent index (proven 2026-08-22) |
| Counting our own imports | imports do not map 1:1 to avatars |

The `/clear-avatars` route and `g_avatarsLoaded` counter remain in plugin v1.3.2 but are **dead code — not called by the pipeline.**

### An intermediate step that did NOT help

`IMPORT_BASE_AVATAR_INTO_CLO = False` in `step_07` — skipping the base import so only the patched avatar loads. Reasoning was sound (the patched `.avt` is a standalone body built from `base-1.avt` on disk; CLO never needs the base loaded), but the counts went **3, 4, 1, 1, 2** — no better.

**Kept anyway**: it removes a genuinely pointless CLO import, and correctness held at 5/5. But it is a tidy-up, **not** the fix. Set it `True` to restore the old behaviour.

## 19. The evidence that identified the race

The user's question: *"is it possible that we are going in a race condition when the next pipeline starts even before the last one completes?"*

Two facts in the code support it:

- **A run ends with no settle.** `step_12` exports the GLB, calls `wait_for_queue`, stops the watchdog, and the process exits. The next `new-project` lands about a second later.
- **`wait_for_queue` does not mean CLO is done.** `new-project-bug-writeup-26_8_9.md` §2 states it outright: *"the command queue reporting empty only proves the command was dequeued and the synchronous SDK call returned — not that CLO's internal engine work is actually done."* `step_11` already carries `MESH_SETTLE_DELAY_SECONDS = 2.5` for the same race at a different call site.

The controlled test — identical five users, only the gap between runs changed:

```
no gap between runs   : 3, 4, 1, 1, 2      erratic, climbing
25s gap between runs  : 3, 1, 1, 1, 1      stable at 1
```

u_011 starts at 3 in both because it inherits leftovers from the previous session. **Every run after it settles to exactly 1 once CLO is given room.**

## 20. The fix

`step_07_import_base_avatar.py`:

```python
CLO_SETTLE_SECONDS = 4.0

wait_for_queue(timeout=30)     # previous run's commands
time.sleep(CLO_SETTLE_SECONDS) # ...and let the engine actually finish them
new_project()
wait_for_queue(timeout=30)
time.sleep(CLO_SETTLE_SECONDS) # let the clear complete before importing
```

Two settles, two reasons: do not ask CLO to clear while it is still writing the previous GLB, and do not import while the clear is still in progress.

**The settle lives inside the pipeline, not the caller.** A pipeline that only behaves when its caller pauses is not fixed — and the worker will pause even less than a test script does.

**No retries around `new-project`**: doc `new-project-bug-writeup-26_8_9.md` §3 records that retrying into a stuck queue was *"confirmed to make things worse, not better."*

**4 seconds, not 25.** The 25s gap proved timing was the variable; it was never tuned. 4s matches `step_11`'s existing 2.5s with margin, and costs ~8s on a ~75s run.

### Verification — five users, back to back, no gaps

```
u_011-005: 1 avatar   78s    168.0 / 92  / 76    OK
u_012-005: 1 avatar   74s    175.0 / 98  / 82    OK
u_013-005: 1 avatar   74s    181.0 / 106 / 92    OK
u_014-005: 1 avatar   73s    186.0 / 100 / 84    OK
u_015-005: 1 avatar     -    186.0 / 112 / 98    OK
```

Measurements read directly from each `result_avatar_from_project.avt` and compared against Mongo — not taken from `run.log`. `u_014` and `u_015` share a height of 186.0 and each received its own chest and waist, so a swap between them would have been visible.

**This is the exact condition that produced 3, 4, 1, 1, 2 before the fix.**

## 21. Corrections to Parts 2 and 3

Recorded explicitly so the earlier text is not acted on as written.

**§9's heading — "Why `new-project` cannot clear avatars" — is WRONG.** `new-project` clears avatars reliably when CLO has settled. What the SDK comment (*"Clear the current garment"*) does not mention, it evidently still does. The empirical claim that avatars survive `NewProject` came from measurements taken during the race.

**§13's design (probe indexes 1 and 2 to prove the scene is clean) is UNSAFE and was abandoned.** `GetAvatarProperties` on an absent index crashes CLO. §12's table calls it "the better probe" — it is not. Do not implement §13.

## 22. Open: replace the guessed delay with a real completion signal

4 seconds is a measured guess, not a guarantee. A slower machine or heavier scene could outrun it. **Deferred by the user, 2026-08-23** — worth doing properly later.

The problem is that the plugin's `asyncResult` is recorded when the SDK call **returns**, which is precisely the thing that does not imply the engine has finished. So the existing per-command result in `/status` cannot be trusted as a completion signal.

CLO exposes exactly three plugin callbacks (`RestPlugin_windows.cpp`):

```
DoFunction()                                  // menu click
DoFunctionAfterLoadingCLOFile(const char*)    // fires after CLO loads a file
DoFunctionContinuously()                      // not called by this CLO version
```

`DoFunctionAfterLoadingCLOFile` is the only genuine "CLO finished something" event available, and it covers file loads only — not saves or exports. **No callback exists for save/export completion.** Nothing was found in the SDK headers matching `after`/`finish`/`complete`/`notify` beyond these.

Options, cheapest first:

1. **Poll the output file for size stability** — after `save-project` or `export`, watch the file until its size stops changing for N consecutive checks. Purely Python, no CLO involvement, and it measures the actual thing we care about. Strongest candidate.
2. **Use `DoFunctionAfterLoadingCLOFile`** to signal load completion specifically — it already fires, it just is not surfaced through the REST API. Only helps the import path.
3. **Ask CLO** whether any completion callback exists that is not in the public headers. Per doc `12`, behaviour is undocumented and support channels are unverified — but this is exactly the kind of question worth spending one ticket on.

Option 1 would remove the guess for the export path entirely and is the recommended next step whenever this is picked up.

# PART 5 — ExportGLB works: one file per run, no packing, no intermediates

Written 2026-08-23, immediately after Part 4's settle fix.

## 24. The problem

A single run produced **33 files, 154 MB**. The glTF half of that was pure intermediate:

```
18 × .jpg + 8 × .png   12.2 MB    CLO avatar textures, written loose
result_avatar.bin      12.8 MB    geometry buffer
result_avatar.glb       0.1 MB    JSON glTF referencing all of the above
result_avatar_packed.glb 29.1 MB  the only file anyone actually uses
```

`ExportGLTF` writes **glTF-separate** — JSON, plus a `.bin` for geometry, plus every texture as a loose file. `step_12` then repacked all of it into a self-contained binary via `pygltflib`.

## 25. A workaround that was proposed and rejected — worth recording

The first fix attempted was to **delete the intermediates after packing**. The user rejected it immediately:

> *"you are saying we first make them and then delete them?"*
> *"this workaround is bad and should never be repeated"*

Correct call. Creating 25 MB and 30 files only to delete them is waste dressed as a fix, and it would have permanently hidden the real problem. **The files should never have been created.** The rejected code was removed in full — no trace remains in `step_12`.

## 26. The actual cause: the same vtable skew as `NewProject()`

`format=glb` requests were being served by `ExportGLTF`, not `ExportGLB`. The plugin comment explaining why said:

> *"ExportGLB always returned an empty result in manual testing ... ExportGLB's declared body in that SDK's header is a bare stub (returns an empty vector) — consistent with this CLO version simply not implementing it yet"*

**That reasoning was wrong**, and `01-how-ai-should-work.md` already recorded it as a misreading: every export method in that header has an empty body, **including `ExportGLTF`, which worked on every single run**. An empty body is the abstract-interface pattern — the real implementation lives in `CLOAPIInterface.dll` and binds at runtime. It proves nothing.

The real cause was **vtable/ABI skew** from building against `CLO_SDK_v2025.2.368` while running a much newer app — the same skew that made `NewProject()` hang until the 2026.0.356 rebuild.

**This is the second bug that theory has now explained.** Both were misattributed to CLO lacking a feature; both were fixed by the same rebuild.

## 27. The change

**Plugin** (`RestPlugin_windows.cpp`, export handler) — honour the requested format:

```cpp
bool wantGLB = (cmd.param2 == "glb");
TraceLog(std::string("BEGIN export format=") + (wantGLB ? "glb" : "gltf") + " path=" + cmd.param1);
std::vector<std::string> out = wantGLB
    ? EXPORT_API->ExportGLB(cmd.param1, options)
    : EXPORT_API->ExportGLTF(cmd.param1, options, false);
TraceLog(std::string("END   export files=") + std::to_string(out.size()));
```

`TraceLog` on both sides, so an empty return is visible rather than inferred.

**`step_12_export_glb.py`** — branch on what CLO actually produced, by magic bytes:

```python
GLB_MAGIC = b"glTF"

def _is_binary_glb(path: Path) -> bool:
    with path.open("rb") as handle:
        return handle.read(4) == GLB_MAGIC

if _is_binary_glb(raw_glb_path):
    ctx.avatar_glb_path = raw_glb_path
    return True                      # single file, nothing to pack
```

Not a flag, not a trusted status field — the first four bytes of the file itself.

## 28. Verified

One run, `u_013-006`:

```
Files produced:  2 .avt, 1 .zprj, 1 .log, 1 .glb        (was 33 files)

result_avatar.glb
  magic bytes    : glTF            <- genuine binary GLB
  loads          : 9 meshes, 26 embedded images, 1 buffer
  external refs  : []              <- fully self-contained
  size           : 37.8 MB
```

| | Before | After |
|---|---|---|
| Files per run | 33 | **5** |
| `.jpg` / `.png` | 26 | **0** |
| `.bin` | 1 | **0** |
| `.glb` files | 2 (JSON + packed) | **1** |

The textures and `.bin` are **not deleted — they are never created.** CLO writes one file, and it is the file the website serves.

## 29. `_pack_self_contained_glb` — keep for now, remove later

The packing path is now dead code on the success path. **Decision, user, 2026-08-23: keep it for the moment; remove it after several more runs confirm `ExportGLB` is reliable.**

It survives as an explicit fallback, and it is loud rather than silent:

```python
ctx.warnings.append(
    "ExportGLB returned JSON glTF rather than binary GLB; falling back to Python packing."
)
ctx.logger.warning("Export produced JSON glTF, not binary GLB - falling back to packing")
```

**The distinction that matters**: this is not the rejected workaround. It does not create files to delete them. It detects that CLO returned the wrong format and salvages the run *while saying so*, instead of hiding a regression behind a cleanup step.

**When to delete it**: once `ExportGLB` has produced binary GLB across a reasonable spread of runs — ideally including a garment-loaded VTO scene, since every run so far has been avatar-only. Delete `_pack_self_contained_glb`, `_is_binary_glb`, and the fallback branch together, leaving the export path a straight line.

**Do not delete it before then.** It is the only thing that would catch a future CLO version regressing `ExportGLB`, and this exact call has silently returned empty before.

## 30. Storage: what this did and did not fix

Per-run cost, measured on `u_015-005` before the change:

```
.avt / .zprj (CLO project)   99.6 MB   64.8%   <- untouched, and NOT in scope
packed .glb (shipped)        29.1 MB   18.9%   <- now the single 37.8 MB file
.bin geometry                12.8 MB    8.3%   <- gone
textures (26 files)          12.2 MB    7.9%   <- gone
raw .glb JSON                 0.1 MB    0.1%   <- gone
```

**The glTF intermediates were never the dominant cost.** Roughly 25 MB of ~154 MB. The bulk is the CLO project files — `result_avatar_from_project.avt` (32.7 MB), `result_avatar.avt`, and `result_project.zprj` (36 MB).

Those are deliberately out of scope (user, 2026-08-23: *"do not go to the .avt file yet"*). They are also load-bearing: the `.zprj` is what `step_11` extracts the verification `.avt` from, and the `.avt` is what the VTO pipeline consumes via `clo_avatar_avt_path`.

Storage pressure remains: `clo_avatar_generation/output/` was **7.8 GB** as of 2026-08-20 with no pruning, and the worker will generate runs far faster than manual CLI testing did. That is a retention-policy question, separate from this one.

**That is no longer true.** It produces binary GLB directly, verified above.
