## 3. Problem 1 — the CLO hang (SOLVED)

### Symptom
Every run died at `step_07_import_base_avatar`:

```
CLO queue did not drain within 30s.
Last status: {'queue_processing': True, 'queue_size': 0}
```

Steps 01-06 always passed. CLO stayed wedged permanently afterwards — `queue_processing` never cleared, and only killing the process recovered it.

### How it was diagnosed
`clo_workspace/logs/plugin_crash_trace.log` showed the exact moment:

```
[10:40:38] tick=187301 heartbeat  queueProcessing=false   ← healthy
[10:40:39] tick=187306 draining queue                     ← batch starts
            (no "tick=187306 drain call returned" ever appears)
[10:40:39] tick=187307 SKIPPED — g_queueProcessing already true
```

The batch contained exactly **one** command — `new-project` — because `step_07` calls `new_project()` and then only polls `/status` (a read, not a queued command). So `NewProject()` itself hung CLO's main thread.

This closed a gap the earlier write-up (`new-project-bug-writeup-26_8_9.md`, §4c) had flagged as unknowable: *which* command was in the stuck batch.

### Root cause
```
CLO app     : upgraded to 2026.1.188 on 2026-08-15 16:04
Plugin DLL  : built 2026-08-03 against CLO_SDK_v2025.2.368 (SDK v9.1.1)
```

The CLO changelog states plainly for **V10.0.2 (June 2026)**:

> *"Plugins built against earlier SDKs must be rebuilt against this SDK."*

— because of a **Qt 6.10 migration**. Confirmed independently on this machine: the CLO window class is `Qt6103QWindowIcon`, and `qtuiotouchplugin.dll` reports 6.10.3.0.

The plugin was pre-Qt6, running inside a Qt6 application. Calls dispatch by **vtable slot index**, so `NewProject()` was landing on the wrong function and blocking. This is the same **vtable/ABI skew** hypothesis recorded in `01-how-ai-should-work.md` for `ExportGLB` — now demonstrated, not just suspected.

### What did NOT cause it — ruled out with evidence
- **Session age.** Suspected at first (10.4 h hung vs 5.5 h worked). Refuted: a **6-minute-old** CLO hung identically.
- **Our plugin code.** The DLL was byte-identical between the 2026-08-09 success and every failure — never rebuilt in between. See doc `09` for the full commit audit.
- **`read-avatar-state`** (the prior investigation's leading theory). Never called on this path.
- **Accumulated queue state.** A fresh process has none.

### The fix, and the false start
The **first** rebuild (14:49) still hung — because the only SDK on the machine was the old `CLO_SDK_v2025.2.368_Win`, so `CLO_SDK_PATH` pointed at it. It recompiled the source but not the skew.

After downloading `CLO_SDK_v2026.0.356_WIN` (SDK v10.0.3) and rebuilding at 15:02:

```
POST /new-project → {"message":"New project created","success":true}
queue_processing: false     (< 2 seconds)
```

**Controlled comparison — same source, same CLO, same command, only the SDK differed:**

| Build | SDK | Result |
|---|---|---|
| 14:49 | v2025.2.368 (pre-Qt6) | hung forever |
| 15:02 | v2026.0.356 (post-Qt6) | succeeded in <2s |

### Note on remaining skew
CLO app is **2026.1.188**; the newest published SDK targets **2026.0.356**. A one-line skew remains and is evidently tolerable — the 2026-08-09 success also ran a slightly-newer app than any SDK. There is no 2026.1 SDK available.

### Still unchanged after the fix
`has_avatar_state_readback` and `has_avatar_avt_export` are still `false`. Same as the working 2026-08-09 run, so nothing regressed — those probes fail for their own reasons.

## 4. Problem 2 — DNS / MongoDB (RECURRING, needs a permanent fix)

### Symptom
The worker dies on its **first** Mongo call (`worker/tasks.py:87`), before any pipeline code runs:

```
dns.resolver.LifetimeTimeout: The resolution lifetime expired after 21.182 seconds:
    Server Do53:192.168.0.1@53 answered The DNS operation timed out ... (×7)
```

### Root cause
The router at `192.168.0.1` **silently drops every DNS response larger than ~512 bytes**. `mongodb+srv://` needs an SRV lookup plus a TXT lookup, and Atlas's reply exceeds that, requiring EDNS0 or TCP fallback — which the router handles for neither.

Proven directly:

```
google.com      192.168.0.1  FAIL LifetimeTimeout 6.4s
google.com      8.8.8.8      OK  15 recs ~854B   0.0s
microsoft.com   192.168.0.1  FAIL LifetimeTimeout 6.4s
microsoft.com   8.8.8.8      OK  61 recs ~4177B  0.1s
cloudflare.com  192.168.0.1  FAIL LifetimeTimeout 6.4s
cloudflare.com  8.8.8.8      OK  28 recs ~2130B  0.0s
```

**A misleading early data point**: a *small* SRV record resolved fine through the router, which made SRV look healthy. **Response size is what matters, not record type.**

**Docker is unaffected** — it resolves through its own resolver inside the Linux VM. That is why the backend worked all day (`/health` → `database: connected`) while the native worker could not connect at all, using the identical URI.

### Why it bit twice more
DNS was at `10.200.1.248` (a VPN resolver) when things worked mid-day, then **reverted to `192.168.0.1`** when the VPN dropped. The 11:04 failure (`SSL handshake failed`, `WinError 10053`) was the same transition caught mid-connection.

### The fix (needs an elevated shell — NOT YET APPLIED)
```powershell
Set-DnsClientServerAddress -InterfaceIndex 7 -ServerAddresses 8.8.8.8,1.1.1.1
# revert: Set-DnsClientServerAddress -InterfaceIndex 7 -ResetServerAddresses
```
Setting it explicitly on the adapter survives VPN transitions. Until this is done, **web-triggered generation cannot work** — the worker will keep dying at `tasks.py:87`.

### Related design point
This is strong support for doc `08` **Concern 11** (worker stops talking to Atlas directly). The pipeline needs *measurements*, not a database connection. The backend, in Docker, was unaffected all day.

## 5. Problem 3 — intermittent `step_11` failure (OPEN, not diagnosed)

### Symptom
```
step_11_save_outputs: failed —
  Saved avatar measurements did not fully match the requested AVT-backed targets.
```

On failing runs, **every** field reports:
```
"delta_from_base": 0.0            ← saved avatar identical to the unmodified base
"delta_from_requested": -2.45 / -2.75 / -3.64 ...
"matches_requested": false
```

`step_08_apply_measurements` reports **passed** on these runs. Only `step_11`'s verification catches it. **Without that check, a failing run would silently publish a base-shaped avatar under the user's name.**

### What the two test rounds showed

| | Test A (20:43) | Test B (23:26) |
|---|---|---|
| Run 1 | **pass** | **pass** |
| Run 2 | fail | **pass** |
| Run 3 | fail | **pass** |
| Run 4 | fail | **pass** |
| Run 5 | fail | fail |

**5 of 10 overall.** Not positional — Test A failed everything after the first, Test B only the last.

### A wrong conclusion, corrected
After Test A I claimed *"generation works once per CLO session"* and blamed stale-scene accumulation. **That was wrong**, and Test B disproved it — four consecutive successes in one session. Recorded here so the mistake is not inherited.

Accumulation would degrade monotonically; it would not allow runs 2-4 and then fail on 5.

### Current best guess (unproven)
A **race**, not accumulation — CLO's internal work not finished when the API call returns. Supporting hint: run timings vary widely (**122s**, 74s, 74s, 71s, 63s) with no correlation to outcome; the *slow* run passed and a *fast* run failed.

This is the failure class `known-issue-26_7_23.md` documents as the "undersized-mesh race", which is why `step_11` already has a settle delay plus retries. The mitigation exists — it just is not always sufficient.

### A confound not yet eliminated
**All 10 runs used identical measurements** (`u_001`'s fixture). If CLO skips work when the avatar already matches the request, that could produce or mask this.

**Prepared but NOT yet run**: 5 fixtures with visibly different bodies, in the session scratchpad as `mvar/v1.json` … `v5.json`:

## 8. A robustness gap seen three times today

When the worker crashes before `tasks.py:93`, the job is left **permanently inconsistent**:

```
Redis : job already dequeued and discarded
Mongo : state still "queued", failure_reason: null
```

Nothing will ever run it, and any UI polling it shows "waiting" forever. This happened after every Mongo-connection crash. It needs an explicit fix — mark the job `failed` on any exception before the state transition, or re-queue it.

Also unlogged: **job creation has no application-level logging at all.** `core/queue.py`, `avatars/engine.py`, and `avatars/service.py` contain zero logging statements between them — the only trace is uvicorn's HTTP access line, which records no job id and no user id. This is why 7 stale jobs accumulated unnoticed earlier in the day.
