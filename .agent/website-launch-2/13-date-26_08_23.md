# 2026-08-23 — how the three pipeline steps are actually wired

Written 2026-08-23, after Part 6 of doc 11 (avatar rendering end to end). Everything below is read from the repo as it stands today, not inferred.

Question set: how the three steps link, what custom input each accepts, how well each logs a run, and what is genuinely on the Redis queue. Written to support three goals: **(1)** show a VTO with clothes, **(2)** reuse the avatar project/GLB we already made instead of accidentally regenerating, **(3)** decide when generation should fire.

Section numbering continues from doc 11 (which ended at §37) so cross-references stay unambiguous.

## 38. The three steps and what each produces

| | Entrypoint | Run folder | Final artifacts |
|---|---|---|---|
| **Step 1** avatar | `clo_avatar_generation/run_avatar.py` | `clo_avatar_generation/output/<user_id>-<NNN>/` | `result_project.zprj`, `result_avatar.avt`, `result_avatar.glb`, `run.log` |
| **Step 2** ingestion | `product_ingestion/run_product_ingestion.py` | `product_ingestion/output/<cloth_id>-<size_id>-<NNN>/` | `panels/dxf/*.dxf`, `panels/textures/*.png`, `image_info/colors.json`, `run_summary.json` |
| **Step 3** VTO | `clo_vto/run_clo_vto.py` | **none — a single shared `clo_vto/output/`** | `simulation.glb`, `simulation_textured.glb`, `<name>__native_vto_report.json` |

Step 3 consumes two things: an avatar `.avt` and a patterns directory of DXF. Those are the only two seams between the steps.

## 39. Seam 1 → 3 (the avatar): sound through the worker, guesswork on the CLI

**Through the worker — this link is real and correct.**

`worker/tasks.py::_run_tryon_render` reads `avatar_profiles.clo_avatar_avt_path`, which `live_upload.save_avatar_version` wrote as `dev_upload/avatars/<user_id>/<NNN>/avatar.avt`. Per-user, versioned, never overwritten. It checks the file still exists on disk and fails the render with a readable reason if not.

**On the CLI — there is no link at all.** `run_clo_vto.py::_discover_default_avt()` searches, in order:

```
clo_vto/output/clo_test.avt
clo_vto/output/*.avt            (only if exactly one)
clo_vto/avt_templates/*.avt     (only if exactly one)
clo_avatar_generation/input/base-1.avt
```

It **never looks in `clo_avatar_generation/output/`**. A CLI VTO run therefore cannot pick up a Step-1 result unless someone copies the `.avt` across by hand. `clo_vto/native_vto/context.py::_discover_default_native_avatar()` duplicates the same search independently — two copies of the same guessing logic.

## 40. Seam 2 → 3 (the garment): this is the missing link, and it is why there are no clothes

**Through the worker there is no link whatsoever.** `_run_tryon_render` calls:

```python
ok = run_vto_pipeline(
    avatar_path=str(avt_path),
    patterns_dir=None,
    use_default_panels=True,      # hardcoded
    ingestion_output_dir=None,    # hardcoded
    report_path=str(report_path),
)
```

`use_default_panels=True` overrides `patterns_dir` to `clo_vto/default_panels/dxf/`, and `ingestion_output_dir=None` means `_resolve_texture_paths_from_ingestion` is never reached — so `colors.json`, the texture atlases, and `graphic_diffuse.png` are all absent and steps 8/12 skip. **Every live try-on renders the same untextured default t-shirt regardless of what the shopper picked.** The existing comment in `tasks.py` says exactly this and points at Step 7.

**The root cause is one missing field.** `SizeDocument` (`website/backend/src/catalog/models.py`) carries `size_id`, `fit_type`, `cloth_id`, `cloth_label`, `category`, and twelve measurement floats — and **nothing pointing at a product-ingestion run**. Grepping the whole backend for `panels_dir` / `patterns_dir` / `dxf` returns zero matches. The backend cannot name a DXF folder because no document tells it where one is.

On the CLI the link exists but is loose: `helpers.resolve_patterns_dir()` → `get_latest_panels_dxf_dir()` returns the newest ingestion run of **any** cloth and **any** size. It matches recency, not the requested garment.

## 41. Custom input: what each entrypoint accepts, and what the web path throws away

**Step 1** — the CLI is the richest surface in the repo:

```
--user-id  --run-number  --base-avatar  --measurement-file
--apply-mode {auto,csv,avatar_properties,avt_patch}  --enable-legacy-route
--active-field (repeatable)  --non-interactive
```

The worker uses **none** of it. `run_avatar_job` hardcodes the default base avatar, `apply_mode="avt_patch"`, no field filters, `measurement_file_input=None` (so measurements come from Mongo), and derives `run_number` from `get_next_run_number`. Only `user_id` varies. That is a defensible product decision — but it means a web-triggered run cannot be reproduced from the CLI without knowing which defaults were in force.

**Step 2** — `--cloth-id --size-id --input-root -o/--output --skip-clip`, and interactive prompts otherwise. **Not reachable from the backend at all**: no task function, no route, no queue entry. Step 2 is CLI-only today.

**Step 3** — CLI: `--avt-path --csv-path --patterns-dir --use-default-csv --report-path --use-default-panels --ingestion-output-dir`. The worker varies only `avatar_path` and `report_path`.

There is also a layer of knobs that `create_context()` accepts but `run_pipeline()` never forwards: `allow_seam_fallback`, `strict_seam_hash`, `strict_dxf_units`. `run_pipeline` takes `seam_map` but `run_clo_vto.py` never passes it. So the strict modes (P07/P08/P10) exist in the context and are **unreachable from either entrypoint** — every run silently gets the permissive defaults, including falling back to `DEFAULT_SEAMS` when a manifest is missing.

## 42. Logging: Step 1 is good, Step 2 is adequate, Step 3 loses data

**Step 1 — the model to copy.**

- Monotonic per-run folder; `get_next_run_number` scans existing dirs, so nothing is ever overwritten.
- `run.log` captures the full run. `logging_setup` buffers step-1 records in a `MemoryHandler` and flushes them into the file once step 2 creates the directory — so even pre-directory lines survive.
- A failed run still gets a directory: `_bootstrap_failure_run_dir` creates one when step 1 itself fails.
- `run_summary` and `output` payloads are written at the end with per-step success/error.
- `live_upload.save_avatar_version` copies `run.log` plus a `run_manifest.json` (with `source_run_id` and `source_run_dir`) next to the shipped artifacts, so a bad avatar on the website traces back to its full debug log.

One wrinkle: steps call `ctx.log_json(...)`, which formats JSON **into the text log**. `ctx.write_json()` exists and writes real `.json` files, but the pipeline does not use it. The structured payloads are greppable, not machine-readable.

**Step 2 — structured, but no log file.** Per-run folder, monotonic numbering, and three good JSON artifacts (`run_summary.json`, `image_info/extraction_metadata.json`, `segmentation_quality.json`). But every progress line is a bare `print()` — nothing captures stdout to disk. If a run misbehaves and the terminal is gone, only the JSON survives.

**Step 3 — this is the weak one, and it silently destroys evidence.**

`create_context` sets `output_dir = clo_vto/output` — a **single fixed directory, not per-run**. `step_11` writes `simulation.glb` and `step_12` writes `simulation_textured.glb` at fixed names. **Every render overwrites the previous render's GLB.** Only the report escapes: the CLI names it `<avt_stem>__native_vto_report.json` and the worker `<render_id>__native_vto_report.json`.

There is no log file at all — `print()` only, throughout. And `_build_report` records `status`, `created_at`, `mode`, per-step results, and a rich `diagnostics` block, but **not the avatar path, the patterns dir, or the render id**. So even the surviving report cannot say which avatar or which garment produced it.

Two renders in a row means the second's geometry replaces the first's, with nothing to reconstruct what the first one was.

## 43. The Redis queue: correct where it exists, and narrower than it looks

**Shape.** One queue, `QUEUE_NAME = "clo"`, carrying both job types. The backend enqueues by string path only (`worker.tasks.run_avatar_job`, `worker.tasks.run_tryon_render`) and never imports the worker package — deliberate, because the backend image has none of the CLO dependencies.

**Concurrency.** `SimpleWorker`, one job at a time, in-process, no fork. Required on Windows and correct regardless: CLO's plugin is single-threaded, so there is no parallelism to win. This is what makes the queue safe — it serialises every CLO touch, which is exactly the property doc 11 Part 4's settle fix depends on.

**Timeouts.** Avatar 20 min, try-on 25 min. Both are explicit and required at the call site — `enqueue()` refuses to default them, so RQ's 180 s default can never leak in.

**What is on the queue:** avatar generation, try-on render. **What is not: product ingestion.** Step 2 has no task function and no route.

Three things worth knowing about the current behaviour:

- **Avatar and try-on share one FIFO.** A 20-minute simulation delays every avatar generation queued behind it. Acceptable with one CLO instance, but it means avatar wait times are not predictable from avatar load alone.
- **There is an enqueue-before-insert race.** Both `avatars/service.py` and `tryon/service.py` call `engine.start_job(...)` / `engine.start_render(...)` **before** `insert_one`. With an idle worker and a slow Atlas write, the worker can pick the job up before its document exists, hit `find_one` → `None`, log `job %s not found, nothing to do`, and return. The job then sits in `queued` forever with no failure reason. The guard exists precisely because this is reachable; swapping the two lines would close it.
- **No retries, no queue visibility.** A failed job is terminal (`_fail_job` writes state and reason). There is no endpoint reporting queue depth or position, so the frontend's only progress signal is polling the job document.

## 44. What each of the three goals actually needs

**Goal 1 — show the VTO with clothes.** Six gaps, in dependency order:

1. `sizes` documents need a pointer to a product-ingestion run (a `panels_dxf_dir` or an ingestion `run_id`). Nothing downstream can be fixed before this exists.
2. `_run_tryon_render` must pass `patterns_dir` / `ingestion_output_dir` derived from the requested garment instead of the hardcoded `use_default_panels=True`.
3. Step 3 needs a per-render output directory — otherwise concurrent-ish renders overwrite each other's GLB (§42).
4. A `save_render_version` mirroring `live_upload.save_avatar_version`, writing the textured GLB to a stable versioned path.
5. A serving route. **`GET /tryon/.../renders/{id}/glb` does not exist** — `tryon/routes.py` has sessions, request, poll, and history, and no file route. `live-schemas.ts:321` hardcodes `renderedAssetUrl: null`.
6. The studio stage renders `previewAssetUrl` as an `<img>` (`avatar-figure.tsx:78`), and `live-schemas.ts` hardcodes `previewAssetUrl: ""`. Showing a real result means putting the R3F viewer from `avatar-glb-viewer.tsx` on that stage.

Items 1–2 are the substance; 3–6 are plumbing.

**Goal 2 — reuse what we made, don't regenerate by accident.** The avatar side is already right: the profile stores `clo_avatar_avt_path` and `avatar_glb_path`, and the VTO imports that `.avt`. Three real risks remain:

- `ProfileAvatar.tsx:63` fires generation whenever `!isLoading && !avatar`. There is **no `isError` guard** — a failed or slow `/avatars/profile` response reads as "no avatar" and starts a real CLO run.
- `regenerate()` starts a fresh run with no confirmation step.
- Staleness is computed and then discarded. `get_profile_glb` derives `is_stale` by comparing `measurements_version`, and the controller ships it as the `X-Avatar-Measurements-Stale` header — **no frontend code reads it**. That header is the honest trigger for "your measurements changed, regenerate?" and it is already there, unused.

VTO's `step_02_new_project` wiping the scene per render is correct, not a bug — it just means the avatar is re-imported on every render, which is unavoidable with one CLO instance.

**Goal 3 — when to fire.** Today generation fires from exactly one place: `ProfileAvatar` on mount when no avatar exists, plus the manual Regenerate button. `useGenerateAvatar` has a single call site. Saving measurements does not trigger anything. Combined with the two points above, the sensible model is: fire on explicit user action, and use the stale header to *prompt* rather than to auto-run — a mount-triggered CLO run is a 90-second job started by a page load.

## 46. Decisions taken in discussion (2026-08-23)

| # | Decision | Reason given |
|---|---|---|
| D1 | **`cloths` and `sizes` are two separate collections, related many-to-many.** A cloth names the sizes it is offered in; a size does **not** name a cloth. | Real companies each have their own cloths and their own size measurements — company A's "M" and company B's "M" are unrelated numbers — so the relationship has to be expressible per company. Many-to-many covers both that and sharing. |
| D2 | **`size_id` stays globally unique** (`s_001`…`s_010`), never restarting per cloth. | One id means exactly one measurement set, wherever it is referenced. |
| D3 | **Demo data: `c_001`–`c_005`, all five referencing the same 10 shared sizes.** | 5 cloth image folders, 5 cloth documents, **10 size documents — the existing ones, unchanged.** See §47. |
| D4 | **Step 2 stays CLI-only.** No queue task, no route. | Ingestion is an operator activity, not a shopper one. |
| D5 | **VTO saves a `.zprj` every run, by default, with no opt-out flag.** | We are testing and will need to reopen failed try-ons in CLO. It also gives VTO the same `.avt`-member avatar count check step 1 uses. |
| D6 | **Old flat output folders are left in place.** | See §52. |
| D7 | **Avatar generation stops firing on page load.** Explicit button; existing GLB is displayed when present. | A page load should not start a 90-second CLO job. |
| D8 | **Retention policy is decided now**, manual and tiered. | `output/` is 7.8 GB with nothing pruning it, and this plan multiplies run count. |

Out of scope, deliberately: the product rail still shows sizes as products rather than cloths with size variants (§44 note); `output/` migration of old runs; replacing the 4 s settle with a real completion signal.

## 47. What D3 means concretely, and the one thing it costs

The mapping lives **on the cloth**, as a list of size ids:

```
cloths
  c_001  size_ids: [s_001 .. s_010]
  c_002  size_ids: [s_001 .. s_010]     same shared sizes
  c_003  size_ids: [s_001 .. s_010]
  c_004  size_ids: [s_001 .. s_010]
  c_005  size_ids: [s_001 .. s_010]

sizes
  s_001 .. s_010                        unchanged, no cloth reference
```

A real second brand later gets `c_020 size_ids: [s_051 .. s_058]` with its own measurements. Nothing about the shape changes — only which ids a cloth points at. That is what keeps D1's real-world requirement satisfied without duplicating measurement rows for the demo.

**The ten existing size documents are not touched at all.** No `cloth_id` field, no backfill, no migration. This is strictly less work than the per-cloth model and every existing ingestion run stays valid.

### What it costs: `cloth_id` is no longer derivable from `size_id`

Under a per-cloth model, `s_001` belonged to exactly one cloth, so the try-on request could keep sending only `sizeId` and the worker could look the cloth up. **With shared sizes, `s_001` belongs to five cloths at once**, so the request must carry both ids. That has a consequence worth stating plainly:

**The catalog remodel moves out of "deferred" and into the critical path.** Today `http-runtime-provider.ts:208` posts `{ sizeId: input.productPublicId }` — the frontend sends the product id *as* the size id, because right now one "product" literally is one size document and the rail shows 10 sizes as 10 products. With 5 cloths sharing 10 sizes that fiction stops working: the rail has to show **5 cloths, with the 10 sizes as variants**, and the render request has to name both.

This is not a large piece of work, and the result is more honest than what exists. But it is a real addition to the plan and it is why §48's ordering changed. See Phase 3b.

Affected: `RequestRenderRequest`, `tryon/service.request_render()`, `TryonRenderDocument`, `catalog.get_garment()`, `listProducts`/`getProduct` in the runtime provider, and the product rail.

## 48. Phase order and why

Two phases come first because they protect everything after them:

- **Phase 1** stops the frontend starting CLO jobs from page loads. With CLO at concurrency 1, an accidental avatar run during ingestion or VTO testing blocks the queue for 90 seconds. Fixing this first makes all later testing predictable. It touches no Python and no CLO.
- **Phase 2** is VTO correctness. It is independent of every layout change and it is the class of bug that produced wrong results silently in step 1.

Then data (3a) → catalog (3b) → ingestion layout and the real ingestion runs (4) → VTO layout and logging (5) → garment wiring (6) → frontend display (7) → retention (8).

Phase 3b was added on review. Under shared sizes the render request has to name both cloth and size, so the catalog can no longer pretend a product is a size — see §47.

## Phase 2 — VTO correctness: settle, avatar count, project save

**Goal.** Port the step-1 fixes that VTO never got. No layout changes in this phase.

**Files:** `clo_vto/native_vto/step_02_new_project.py`, `step_03_import_avatar.py`, `client.py`, a new `step_10b`-equivalent or an extension of `step_11`.

**Steps**

1. **Settle around `new_project`.** `step_02` currently queues the command, does a best-effort 30 s drain, and returns on "command accepted". Mirror `step_07_import_base_avatar`'s pattern exactly: `wait_for_queue` → sleep `CLO_SETTLE_SECONDS` → `new_project()` → `wait_for_queue` → sleep again. Reuse the same 4.0 s constant and reference doc 11 Part 4 in a one-line comment.

   This matters more here than in step 1. Step 1's final fix was to *delete* an import (`IMPORT_BASE_AVATAR_INTO_CLO = False`), because `ImportAvatar` always ADDs and the SDK has no replace flag. VTO cannot use that escape hatch — it must import an avatar — so it runs precisely the `new_project` → `import_avatar_avt` sequence that yields two avatars when the clear has not landed.

2. **Clean-scene assertion after import.** Add `get_avatar_count()` to `clo_vto/native_vto/client.py` (the plugin route already exists; `avatar_runtime/client.py:69` uses it). In `step_03`, after the import drains, assert the count is exactly 1.

   **On failure, fail the run and say so. Do not delete anything.** `v_1.3.2.json` records that `DeleteAvatar` hangs CLO and `GetAvatarProperties` crashes the process on a bad index; doc 12 §2 establishes `GetAvatarCount()` as the only documented-safe index query. Cleanup-after-the-fact is also the pattern rejected on 2026-08-23 — the point is that the second avatar should never exist.

3. **Save the project (D5).** Add a save-project call producing `simulation.zprj` in the run directory, after simulation and before export. Then reuse step 1's `count_project_avatars()` / `_select_member()` logic to verify the saved project holds exactly one `.avt` — the same check step 1 uses, now available to VTO because we are saving a project.

4. **Magic-byte check on the exported GLB.** `step_11` requests `format="glb"` and, since the SDK-matched plugin rebuild, gets real `ExportGLB` output. It never verifies this. Port `_is_binary_glb()` from `clo_avatar_generation/.../step_12_export_glb.py`. If CLO ever falls back to glTF-separate, 26 loose textures reappear in the run directory and today nothing would say a word.

   Checked and **not** a bug: `step_12_texture_glb` uses `GLTF2().load()`, which sniffs the magic and dispatches, so it already handles binary GLB correctly. No change needed there.

**Verification:** five back-to-back VTO runs against the same avatar. Every run must report avatar count 1 both from `GetAvatarCount` and from the saved `.zprj`, and every exported GLB must start with `glTF`. This mirrors the five-run protocol that validated the step-1 settle fix.

## Phase 5 — VTO output layout and logging

**Goal.** `output/<user_id>/<cloth_id>/<size_id>/<NNN>/`, plus a real log.

**Files:** `clo_vto/native_vto/context.py`, `pipeline.py`, `step_11_export_note.py`, `step_12_texture_glb.py`, `clo_vto/run_clo_vto.py`, new `clo_vto/native_vto/logging_setup.py`, `worker/tasks.py`.

**Steps**

1. `run_pipeline()` gains `user_id`, `cloth_id`, `size_id`. It currently knows none of them, which is the whole reason the output directory cannot be per-run.
   - **Worker:** `user_id`, `cloth_id` and `size_id` all come off the render document — which is why Phase 3b has to land first. With shared sizes there is no size→cloth lookup available (§47).
   - **CLI:** explicit `--user-id --cloth-id --size-id` flags. Not derived from paths — the existing `_discover_default_avt()` guessing is how this got loose in the first place.
2. `create_context` builds the nested run directory with per-key monotonic numbering, same convention as steps 1 and 2. `project_dir` becomes per-run rather than a shared `output/projects/`.
3. `simulation.glb`, `simulation_textured.glb` and `simulation.zprj` now live in the run directory. **This alone fixes §42's silent overwrite** — the fixed names stop colliding the moment the directory is per-run.
4. Port `logging_setup.py` from `clo_avatar_generation/avatar_runtime/` essentially unchanged: console + file, `MemoryHandler` buffering pre-run-dir records and flushing them into `run.log`. Replace `print()` throughout the step modules. This is the single biggest observability win in the plan — VTO currently writes nothing to disk.
5. Create the run directory before step 1 so a failure still produces one, mirroring `_bootstrap_failure_run_dir`.
6. `_build_report` gains an `inputs` block: avatar path, patterns dir, render id, user/cloth/size. Today it records rich diagnostics but nothing identifying what produced them. Always write it into the run directory, not only when `report_path` is passed.

**Verification:** two consecutive renders for the same user/cloth/size produce `001/` and `002/`, both complete, neither overwriting the other. A deliberately failed render still leaves a directory with a `run.log` and a report.

## Phase 6 — wire the real garment through the worker

**Goal.** Stop every try-on rendering the same default t-shirt.

**Files:** `worker/tasks.py`, `clo_vto/native_vto/pipeline.py`.

**Steps**

1. `_run_tryon_render` currently hardcodes `use_default_panels=True, ingestion_output_dir=None`, which forces `clo_vto/default_panels/dxf/` and skips every texture step. Replace with the latest ingestion run directory for the render's `(cloth_id, size_id)` — reachable now that Phase 3b puts both ids on the render document and Phase 4 gives the tree.
2. Fail the render with a readable reason when no ingestion run exists for that pair, rather than silently falling back to default panels. Silent fallback is what made this invisible for so long.

## Phase 7 — serve and display the VTO

**Goal.** The try-on result reaches the browser.

**Files:** new `worker/live_upload.py` function, `website/backend/src/tryon/{routes,controller,service}.py`, `website/frontend/src/integrations/mirra-api/live-schemas.ts`, `features/studio/components/avatar-stage.tsx` / `avatar-figure.tsx`.

**Steps**

1. `save_render_version()` mirroring `save_avatar_version()` — copy the textured GLB, `run.log` and a `run_manifest.json` into a stable versioned path under the upload root. Store the relative path on the render document.
2. `GET /tryon/sessions/{sid}/renders/{rid}/glb`. **This route does not exist** — `tryon/routes.py` has sessions, request, poll and history, and no file route. Model it on `avatars/routes.py`'s `/profile/glb`, including the traversal guard and ownership check.
3. `live-schemas.ts:321` hardcodes `renderedAssetUrl: null`. Map it from the render document.
4. The studio stage renders `previewAssetUrl` as an `<img>` (`avatar-figure.tsx:78`) and `live-schemas.ts` hardcodes `previewAssetUrl: ""`. Replace with the R3F viewer already working in `avatar-glb-viewer.tsx`.
5. Before any render exists in a session, the stage shows the plain avatar GLB from `/avatars/profile/glb`. The viewer component is the same; only the source URL differs.

**One GLB, not two — verified 2026-08-23.** `RestPlugin_windows.cpp:1825-1826` sets `bExportAvatar = true` unconditionally and `bExportGarment = (g_patternsLoaded > 0)`, so a VTO export contains **avatar and garment in a single file**. There is no compositing to do in the browser, and it is also why the avatar-only export in step 1 works — `g_patternsLoaded` is 0 there.

**Verification:** pick a garment in `/studio`, wait for the render, see it on the avatar in 3D. Switch cloths and confirm the figure changes.

**Known issue carried in, not fixed here:** the viewer re-downloads the whole GLB on every mount because the authed fetch bypasses the route's `immutable` cache header (doc 08 Concern 12). This bites harder once display is the common path rather than the rare one.

## Phase 8 — retention

**Goal.** A decided, manual, tiered policy (D8).

**Files:** new `scripts/prune_output.py`.

**The line that must not blur:** `clo_*/output/` is a debug trail; `dev_upload/` is the product. Retention applies **only** to the debug trail. Nothing automatic ever touches `dev_upload/` — that is what the website serves and what `avatar_profiles.avatar_glb_path` points into.

**Policy**

- Keep the last **3 runs per key** — per `user_id` for avatars, per `(cloth, size)` for ingestion, per `(user, cloth, size)` for VTO. The nested trees make this a directory listing rather than a glob.
- Never delete the newest run for a key, whatever its age.
- Never delete a run younger than 7 days, even beyond the 3.
- **Tiered, not binary.** For runs falling out of the window, delete the heavy files (`.zprj`, `.avt` — 65% of a run per doc 11 §30) and keep `run.log`, `run_summary.json` and the `.glb`. "What happened on run 42" stays answerable long after the geometry is gone.
- **Manual and explicit**, `--dry-run` first. Never automatic at the end of a pipeline run: pruning while CLO or the worker may be mid-read is how you lose the run you needed, and it should never surprise you.

## 50. Risks

- **Phase 3b changes a live request contract.** `RequestRenderRequest` gains a field and the rail changes what a "product" is. Backend and frontend must move together; a half-applied change leaves the studio requesting renders for ids that no longer mean what the server thinks.
- **Phase 5 changes a shared signature.** `run_pipeline()` has two callers; both must move together or the worker breaks silently at import time.
- **Phase 2 and Phase 5 both touch CLO.** Concurrency is 1 — one agent, one worker, no parallel testing. Phase 1 landing first is what makes this tractable.
- **50 ingestion runs plus 25 VTO runs on top of an existing 7.8 GB.** Phase 8 should not slip much further than Phase 5.
