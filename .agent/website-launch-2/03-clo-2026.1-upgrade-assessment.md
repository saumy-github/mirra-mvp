# 03 — CLO 2026.1.188 upgrade assessment (research only)

**Installed:** CLO **2026.0.374** · **Offered:** CLO **2026.1.188** (released 2026-08-13)
**Status of this doc:** research only. No code changed, no CLO interaction, nothing upgraded.

---

## Verdict

**Don't upgrade now. Revisit after the pilot ships — and when you do, upgrade the *SDK* first, not the app.**

Three findings drive this:

1. **The thing we actually want from an upgrade (real binary GLB export) is almost certainly an *SDK* change, not an *app* change.** Our "ExportGLB is an unimplemented stub" finding was made against `CLO_SDK_v2025.2.368` — a 2025-line SDK, one full major line behind the app we already run. CLO's official API changelog shows an actively maintained, bug-fixed GLB exporter in the current V10.x SDK line (June–July 2026). We may be able to delete the Python packing workaround **without touching the CLO app at all.**
2. **Nothing in the 2026.1 app release notes touches the plugin API.** Every listed fix is GUI, rendering, or file-format behaviour. Both new features are windows. There is no stated automation upside to the app upgrade specifically.
3. **The rollback path is not confirmed.** CLO's download page offers only the latest build (2026.1.188). There is no public archive of older installers, and CLO's own downgrade guidance is a full uninstall including registry deletion. On a single, non-redundant CLO instance that all three pipelines depend on, an upgrade you cannot cleanly undo is the wrong risk to take during launch prep.

The upside on offer is deleting a workaround that already works and is already verified. The downside is all three pipelines down with an uncertain recovery path. That trade is bad right now and fine in a quiet week after the pilot.

**One cheap, zero-risk action is worth doing now** (details in Q1): read `ExportAPIInterface.h` in the `CLO_SDK_v2026.0.262_Mac` package already on the Mac. It answers the highest-value question — is `ExportGLB` still a stub? — with no download, no build, no CLO interaction.

## Q1 — Does a newer CLO implement binary GLB export?

**Answer: strong evidence yes in the current SDK line — but not confirmed for our build, and the fix is gated behind an SDK upgrade, not the app upgrade being offered.**

### What we depend on today

`clo_avatar_generation/avatar_runtime/step_12_export_glb.py` exports via the plugin, then repacks in Python with `pygltflib` (`convert_images(DATAURI)` + `convert_buffers(BINARYBLOB)`), and round-trips through `GLTF2().load_binary()` to verify. That workaround is sound and self-verifying.

The plugin source states the constraint precisely — `clo_workspace/windows/RestPlugin_windows.cpp:1773-1784`:

> `// options - the installed CLO app is 2026.0.374 while this plugin builds`
> `// against CLO_SDK_v2025.2.368, and ExportGLB's declared body in that SDK's`
> `// header is a bare stub (returns an empty vector) - consistent with this`
> `// CLO version simply not implementing it yet, rather than an options bug.`

**This is the load-bearing detail the earlier write-up understates.** The stub was observed in the **2025.2.368 SDK header**. It is a property of the SDK we compile against — *not* a proven property of CLO 2026.0 or 2026.1. `.agent/website-launch-2/01-how-ai-should-work.md` records this as "not possible on this CLO version"; the more precise statement is "not possible with this **SDK** version."

The plugin calls `EXPORT_API->ExportGLTF(cmd.param1, options, false)` — passing `false` for `bGLBinary`, so glTF-separate output is expected behaviour there regardless.

### Official evidence that GLB export is real in the current SDK line

From the [CLO API changelog](https://developer.clo3d.com/changelog.html) (**official documentation**):

- **V10.0.3 (July 2026):** "Fixed an issue where the GLB exporter set the z-offset of graphics to -1, making the graphics not appear on renders." and "Fixed the GLB exporter omitting the `source` field on the textures array."
- **V10.0.2 (June 2026):** "Fixed an issue where the `ExportGLTF` API failed to create a GLB file when zip output was enabled."
- **V8.0.6 (November 2025):** "Fixed an issue where incorrect UV data was exported when using Unified Mapping Type Material via API."

From the [CLO API list](https://developer.clo3d.com/list.html) (**official documentation**), `ExportGLB` is documented with a real signature, alongside variants:

```
def ExportGLB(_filePath : str, _options : ImportExportOption) -> list[str]
def ExportGLBW(_filePath : str, _options : ImportExportOption) -> list[str]
def ExportGLBWithDialog(_filePath : str) -> list[str]
def ExportGLTF(_filePath : str, _options : ImportExportOption, _bGLBinary : bool) -> list[str]
```

**Inference (mine, clearly labelled):** you do not write three separate bug fixes against a GLB exporter's texture `source` field and graphic z-offset unless that exporter is producing real GLB files that real users are inspecting. Combined with `ExportGLB` being documented rather than deprecated, this is good evidence that binary GLB export is implemented and maintained in the V10.x SDK line.

**What is NOT confirmed:** that `ExportGLB`'s body is non-stub in any specific SDK package. Documentation listing an API is exactly what we already had for 2025.2.368 — where the header body was still empty. Only reading the header settles it.

### The cheap test that settles this — zero risk

`clo_workspace/mac_plugin_setup.md` records that **`CLO_SDK_v2026.0.262_Mac` is already downloaded** on the Mac (`~/Downloads/`). Reading `ExportAPIInterface.h` in that package shows immediately whether `ExportGLB`'s declared body is still a bare stub in the 2026.0 line. No CLO interaction, no build, no install — just opening a header file. Do this before spending anything else on the question.

If 2026.0.262 still stubs it, the next check is a V10.x SDK download (also free, also offline).

### Knock-on value

`clo_vto/native_vto/step_12_texture_glb.py` does have the identical gap: it calls `GLTF2().load(...)` at line 277 and `gltf.save(...)` at line 309 with **no** `convert_images` / `convert_buffers` packing anywhere in the file (verified by grep — zero matches). If a working `ExportGLB` landed, both steps simplify. If it doesn't, the VTO step can be fixed today by copying the avatar step's proven packing helper — **that fix does not require any upgrade at all**, and is the better near-term move.

## Q2 — Do the DXF import fixes affect us?

**Answer: they touch structures we genuinely emit, but we have no logged symptom matching either fix, and DXF fidelity is not currently the binding constraint. Low priority.**

### What we actually emit

`product_ingestion/clo_block/clo_dxf_writer.py` is an AAMA/ASTM DXF R12 writer that deliberately mirrors CLO's own export structure. It writes, by numeric layer:

| Layer | Content |
|---|---|
| 1 | closed `POLYLINE` — sewing line, the boundary CLO reads |
| 2 | `POINT` per turn point |
| 3 | `POINT` per curve point |
| **4** | **`POINT` per notch**, `Z = 7.0`, group code 50 = inward normal angle |
| 7 | `LINE` — grainline |
| 8 | `POLYLINE` — internal construction lines |
| **84** | **seam allowance** — offset `POLYLINE` (written when `cfg.seam_allowance_mm > 0`) |

So **both** 2026.1 DXF fixes land on structures we produce: we write notches, and we write seam allowance. The file is also assembled as a `BLOCK` with a single `INSERT` in the `ENTITIES` section.

An older second writer also exists — `product_ingestion/panel_export_dxf.py` (ezdxf, R2010, `LWPOLYLINE`, notches on a *name*-based layer `"Notch"`). `clo_dxf_writer.py`'s own header comments call that approach wrong for this target, since CLO exports R12 where `LWPOLYLINE` does not exist and AAMA identifies content by numeric layer.

On the import side the plugin is thin — `RestPlugin_windows.cpp:1708-1713` sets `ImportDxfOption` scale and `m_bAppend = true`, then calls `IMPORT_API->ImportDXF(...)`. No notch or seam-allowance handling of our own to be affected.

### Why the impact is low anyway

- **`clo_vto` isn't consuming graded, per-product DXF yet.** `.agent/website-launch/06-avatar-vto-implementation-status.md:110` records that every catalog entry, regardless of `cloth_id`, renders from the same single hardcoded placeholder pattern set in `clo_vto/default_panels/dxf/` — `cloth_id` is stored but never used to select patterns. Those four `.dxf` files aren't even tracked in the repo (a repo-wide `**/*.dxf` glob returns nothing; they're local/generated per `default_panels/README.md`).
- **No matching symptom is documented anywhere.** Grepping `.agent/` for notch / seam-allowance / DXF-failure notes turns up only the placeholder-panels gap above. `.claude/troubleshooting.md` has generic "DXF Generation Fails" / "DXF files invalid" entries — nothing resembling "notches in the wrong position" or "some patterns silently missing".

**Inference (mine):** "some patterns not imported when loading DXF files" is the fix I'd watch most, because a `BLOCK`/`INSERT`-structured file with one insert per piece is plausibly the shape of file that trips that class of bug, and the failure mode is *silent* — a missing panel, not an error. But this is speculation about a bug whose reproduction conditions CLO didn't publish. We have no evidence we're hitting it.

**Practical read:** treat these fixes as "might quietly improve pattern fidelity later", not as fixing anything we're currently fighting. They become genuinely interesting *after* per-product graded DXF is wired into `clo_vto` — i.e. after the placeholder-panels gap is closed, not before.

## Q3 — Is the REST plugin version-locked, and what is the upgrade risk?

**Answer: yes, version-coupled and officially so. But the risk on *this Windows machine* is narrower than it first looks, and the real blocker is the rollback path, not the API.**

### Official: CLO says plugins must be rebuilt

- [CLO API changelog](https://developer.clo3d.com/changelog.html), **V10.0.2 (June 2026)**: *"Migrated the CLO SDK to Qt 6.10.x. **Plugins built against earlier SDKs must be rebuilt against this SDK.**"*
- [Environment Setup & Plug-in Build](https://developer.clo3d.com/environment.html): *"CLO 2026 and later: Use Qt 6.10.1"*, *"CLO 2025 and earlier: Use Qt 5.15.16"*, and *"Please ensure you are using the correct Qt version for your target CLO version."* Also: Release builds only — *"Debug binaries (`.dll`/`.dylib`) will not load in CLO."*
- The changelog also shows **API removals**: V10.0.0 removed `GetFabricSize`; V10.0.3 removed Pattern CPX and `ReDrape3DArrangement`. (**Inference:** removing methods from pure-virtual interface classes shifts vtable layout, which is precisely why a plugin compiled against older headers must be rebuilt. Good news: I grepped `clo_workspace/` — **we use none of the removed APIs.**)

Our own `clo_workspace/SETUP.md` already states the rule under Required Software: *"CLO SDK matching your CLO build."*

### We have already lived through this exact break — on macOS

`clo_workspace/mac_plugin_setup.md` §3.1 is a first-hand account, written 2026-08-04 after the first successful Mac build:

- **Symptom:** build succeeds, then CLO shows *"The plug-in has a problem. Do you want to remove the plug-in?"*
- **Cause:** the plugin doesn't link Qt; it expects Qt symbols to resolve from CLO's already-loaded Qt at runtime. **CLO 2026 ships Qt 6.10.3 and no Qt5 at all**, so a Qt5-header build cannot resolve. Three specific symbols are named (`QArrayData::shared_null`, `QArrayData::deallocate`, `QString::fromUtf8_helper`).
- **Fix:** `Qt5` → `Qt6` in `mac/CMakeLists.txt`, SDK `2026.0.262`, Homebrew Qt 6.11.1, `QT_NO_VERSION_TAGGING` to bridge 6.11.1-vs-6.10.3.

That doc's own advice is the right instinct here: *"CLO's Qt version ← check this first on any new CLO release."*

### Why Windows is materially safer than Mac was

**The Windows plugin has no Qt dependency at all.** Verified directly:

- `clo_workspace/windows/CMakeLists.txt` contains no `find_package(Qt...)`, no Qt include dirs, no Qt link targets. It links exactly two things: `CLOAPIInterface` and `Dbghelp.lib`.
- `RestPlugin_windows.cpp` includes **zero** Qt headers (grep for `#include <Q` / `QtCore` / `QString` returns only one passing comment at line 190).

So the Qt5→Qt6 break that killed the first Mac build **cannot hit the Windows plugin the same way.** Windows' exposure is narrower: the C++ ABI of `CLOAPIInterface.dll`.

And there is real empirical comfort there: **the Windows plugin builds against `CLO_SDK_v2025.2.368` and runs correctly on app `2026.0.374` right now.** That is a plugin already surviving a full major-line skew between SDK and app. (Caveat: a sample of one, and it directly contradicts the vendor's stated Qt rule — we're relying on an unsupported-but-working configuration. Don't mistake it for a guarantee.)

The Mac side is already on the newer footing (SDK 2026.0.262 + Qt6), so a Mac rebuild against a V10 SDK is a smaller step than a Windows one.

### The actual blocker: rollback is not confirmed

- The [CLO download page](https://www.clo3d.com/en/clo/download) offers **only** the latest build — 2026.1.188, updated August 13, 2026. **No public archive of older installers.** (official)
- CLO community/support threads on installing a previous version point to logging in and/or contacting support, and CLO's own uninstall guide is heavy: uninstall all CLO products, delete registry key `Computer\HKEY_CURRENT_USER\Software\CLO Virtual Fashion`, delete `C:\Program Files\CLO{product}` and the CLO Assets folder. (**community report + official support article**, not a guaranteed self-serve downgrade)
- **NOT CONFIRMED:** that 2026.0.374 can be re-obtained on demand.

**Plugin-side rollback, by contrast, is clean and ours.** Per `clo_workspace/README.md`: versioned builds in a machine-local vault, `switch_plugin.py --list` / `--activate 1.1.0`, single-version invariant enforced (two DLLs in the plugins folder both load and fight over port 50505). But that rolls back **the plugin, not the CLO app** — it doesn't help if the app itself is the problem.

**Net risk assessment:** probability of the Windows plugin breaking on 2026.1 is *moderate-low* (no Qt exposure, no removed APIs in use, one major-line skew already survived). Impact if it breaks is *total* — no `localhost:50505` means avatar generation, product ingestion, and VTO are all down at once. And recovery depends on an installer we have not confirmed we can get back.

## Q4 — Are Pattern Information and 2D Grading Review useful to us?

**Answer: no. Both look GUI-only, and our grading happens upstream in Python anyway.**

Being concrete rather than dismissive:

- Both features are described in the update dialog as *windows* — "manage key properties of 2D patterns in one window", "compare/review 2D patterns and graphic placement across all grading sizes in a single window". That framing is inherently interactive.
- **Grading Review already exists as a GUI feature** in CLO — there is a long-standing [support article for it](https://support.clo3d.com/hc/en-us/articles/360055936213-Grading-Review). 2026.1's "2D Grading Review" reads as an extension of an existing GUI tool rather than a new capability. (official doc exists; **inference** that 2026.1's is an extension of it)
- I found **no** grading-review or pattern-information API in the CLO API reference. The nearest grading-adjacent API surface in the changelog is `ImportPatternJSON` (which carries grading sizes — v7.0.0 fixed "the smallest grading size was unintentionally removed when using ImportPatternJSON") and "Pattern API print layout sizing" (V9.1.1). Neither is a review window.
- **Our grading is upstream.** `product_ingestion` generates graded DXF per size in Python before CLO ever sees it. A CLO-side visual review window has no insertion point in a headless pipeline.

**Honest caveat:** my fetch of the API list page returned a partial view (it's a large page and the summarizer surfaced only some sections). "No grading API found" is *not found*, not *proven absent*. But given both features are explicitly windows, the conclusion holds regardless.

**Where they could have indirect value:** as a *manual debugging aid* for a human inspecting why a graded pattern set looks wrong — Pattern Information's per-pattern revision history and the grading comparison view are decent eyeball tools. That's a nice-to-have for whoever authors patterns by hand, not a pipeline capability. It does not justify upgrade risk.

## Q5 — Anything else that matters

The most useful discovery here is a framing one: **the app-level 2026.1 release notes and the SDK-level API changelog are different tracks, and everything that would actually help us is on the SDK track.** Nothing in the 2026.1 dialog list mentions the plugin API at all.

From the [CLO API changelog](https://developer.clo3d.com/changelog.html) (**official**), ranked by relevance to us:

- **V9.1.1 (March 2026): "Improved `ImportAvatar` API to load without Size and Pose dialog."** Highest-value item found outside Q1. A modal dialog appearing mid-import is exactly the failure mode that hangs a headless, single-threaded command queue.
- **v8.0.3: "Fixed incorrect avatar height when using `ImportAvatarMeasure`."** We call `ImportAvatarMeasurement` (`RestPlugin_windows.cpp:1634`, `RestPlugin_macOS.cpp:643`), and `clo_workspace/versions/v_1.3.0.json` still lists *"Native avatar measurement CSV import remains under investigation"* as an open known issue. **Possibly a direct fix for a bug we still carry** — though I could not confirm that `ImportAvatarMeasure` and `ImportAvatarMeasurement` are the same call, nor that v8.0.3 postdates our SDK. Worth checking against the newer SDK headers during the same offline read proposed in Q1.
- **V10.0.2 (June 2026): "Added an API to get the patterns attached to a given avatar measure."** Potentially interesting for measurement-driven fit work later.
- **V10.0.1 (May 2026): "Fixed Windows CLO launch intermittent crash."** Mildly relevant given we depend on one always-on instance.
- **V10.0.0 (May 2026):** added CLO file validation, topstitch export, Python support for library management and auto-load; removed `GetFabricSize`.
- **V10.0.3 (July 2026):** removed Pattern CPX and `ReDrape3DArrangement` APIs — **we use neither** (grep-verified).

Simulation quality: nothing in the SDK changelog. The 2026.1 dialog's "trims with thin collision thickness simulated incorrectly" fix is the only simulation item, and we don't currently simulate trims.

**No public 2026.1.188 release notes and no community field reports exist yet.** The release is two days old (2026-08-13 vs today 2026-08-15); CLO's release-notes section returned HTTP 403 to automated fetching, and searches surfaced nothing 2026.1-specific. Searches did surface a general pattern of CLO point updates causing user-visible breakage (a blank/black workspace after update; simulation stopping on Mac after an update) — **community reports about other versions**, not 2026.1, but they support the general "let a point release age" instinct. Being the early adopter of a two-day-old build on your only CLO instance during launch prep is the whole risk in one sentence.

## What we'd need to test before trusting an upgrade

Ordered cheapest/safest first. Items 1–3 involve **no CLO interaction at all.**

1. **Read `ExportAPIInterface.h` in `CLO_SDK_v2026.0.262_Mac`** (already on the Mac). Is `ExportGLB`'s body still a bare stub? Offline file read. This alone may decide whether any upgrade is worth pursuing.
2. **If still stubbed, download the current V10.x SDK and read the same header.** Free, offline, no install. Also check `ImportAvatarMeasure`/`ImportAvatarMeasurement` while there.
3. **Confirm you can get CLO 2026.0.374 back.** Check for an archived installer locally; if absent, ask CLO support *in writing* whether older installers are available before upgrading. **Treat this as a hard gate — do not upgrade until it is answered.**
4. **Check the app's Qt version after any upgrade, before rebuilding anything.** Mac: `otool -L /Applications/CLO.app/Contents/MacOS/CLO_Standalone_OnlineAuth | grep -i qtcore`. Windows: inspect the CLO install dir for `Qt6*.dll` vs `Qt5*.dll`. Windows has no Qt dependency, so this is informational there and load-bearing on Mac.
5. **Rebuild the plugin against the matching SDK, Release only**, bumping the version in `clo_workspace/versions/` first (per README: rebuilding without a bump overwrites the vault entry). Keep the current DLL in the vault so `switch_plugin.py --activate` can restore it.
6. **Smoke the plugin before any pipeline run:** `/health` (version, `plugin_built_at`, `contract_version`), then `/capabilities`, then the trace log. If the plugin doesn't load, CLO shows the "The plug-in has a problem" dialog — that's the signature failure.
7. **Then, and only then, one full run of each pipeline, strictly serialized** — never two at once (`01-how-ai-should-work.md`: concurrency = 1, and the user must not be using CLO at the same time). Avatar → check the packed GLB actually opens; ingestion → check panel count and that no pattern silently went missing on DXF import; VTO → check simulation and textures.
8. **Diff artifacts against a known-good run**, don't just check for absence of errors. Panel counts and notch positions are the two things the 2026.1 DXF fixes could change *silently*. A run that "succeeds" with a missing panel looks identical in the logs.
9. **Budget a contiguous half-day minimum** with CLO unavailable to everyone else, and do it with the pilot not imminent.

## Recommended timing

**Do not upgrade during launch prep.** Concretely:

- **Now → pilot launch:** freeze CLO at 2026.0.374. Do items 1–3 above (all offline, all free). If item 1 or 2 shows a real `ExportGLB`, that's a strong reason to schedule the work — but schedule it, don't do it.
- **Also now, independent of any upgrade:** port the proven packing helper from `step_12_export_glb.py` into `clo_vto/native_vto/step_12_texture_glb.py`. It fixes the known VTO GLB gap today, at zero upgrade risk, and it stays correct whether or not we ever upgrade.
- **After the pilot, in a deliberately quiet window:** do the SDK upgrade (not necessarily the app upgrade) with the full test list above. By then 2026.1.188 will also have aged past the point where day-one regressions are still undiscovered.
- **Only upgrade the app if a header read proves the GLB fix requires it**, or if a specific bug we're actually hitting is fixed there. Right now, neither is established.

The asymmetry is the whole argument: the reward is deleting a workaround that already works and is already verified; the risk is all three pipelines down on a single non-redundant instance, with a rollback we have not confirmed exists.
